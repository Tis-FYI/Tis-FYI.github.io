0.2 你该知道的 5 件事

  1. Kafka 3.x 仍支持 ZooKeeper，但官方已宣布 4.0 起移除 ZK。所以 3.x 是 ZK 模式的”最后一站”，运维上要提前规划向 KRaft 迁移。

第 1 章 Kafka 核心概念与架构

1.1 一句话理解 Kafka

Kafka 是一个分布式的、分区的、多副本的提交日志（Commit Log）系统，本质上是一个”可以持久存储、可以被多方重复读取、可以水平扩展的消息队列”。

1.2 核心概念对照表

概念 说明 运维关注点
Broker 一个 Kafka 服务进程/节点 单节点承载能力、磁盘、网络
Topic 逻辑消息分类，类似”表” 分区数、副本数、保留策略
Partition Topic 的物理分片，是并行与顺序的最小单位 数量决定并发度，不可减少
Replica 分区的副本，分为 Leader / Follower 副本数决定容灾能力
Leader 处理所有读写的副本 Leader 分布是否均衡
Follower 只做同步，不对外提供服务 ISR 同步延迟
ISR In-Sync Replicas，与 Leader 保持同步的副本集合 核心健康指标，ISR 收缩 = 有风险
OSR Out-of-Sync Replicas，落后过多的副本 长期 OSR 会拖慢 Leader
Controller 集群中负责分区 Leader 选举、元数据管理的 Broker 单点，需关注切换
ZooKeeper 存储集群元数据、Controller 选举、ACL 3.x 强依赖，必须高可用
Offset 消息在分区内的唯一递增编号 消费进度、滞后量
Consumer Group 消费者组，组内分区消费分摊 再平衡（Rebalance）
Segment 分区目录下的日志文件分片 文件数量、清理策略
HW (High Watermark) 消费者可见的最高 offset 影响消费延迟
LEO (Log End Offset) 分区日志末尾 offset LEO - HW = 副本延迟
LSO (Last Stable Offset) 事务场景下稳定 offset 事务消息排查

1.5 副本同步机制（LEO / HW / ISR）

这是 Kafka 可靠性的核心，运维必须清楚：

触发 ISR 收缩的条件（由 replica.lag.time.max.ms 控制，默认 30000ms）：

  • Follower 在 30 秒内没有向 Leader 发起 fetch 请求，或
  • Follower 的 LEO 落后 Leader 超过 30 秒（注意：是时间不是条数！3.x 已废弃 replica.lag.max.messages）

ISR 收缩的后果：

  • acks=all 的写入只需 ISR 内副本确认 → 变快但可靠性下降
  • 若 ISR 缩到只剩 Leader，此时 Leader 宕机 → 数据丢失

⚠️ 运维红线：必须配置 min.insync.replicas >= 2，否则 ISR 缩到 1 时 acks=all 形同 acks=1。

1.6 Leader 选举机制

场景 选举方式 是否丢数据
Leader 宕机 从 ISR 中选新 Leader（Controller 主导） 不丢（ISR 内的都同步过）
ISR 全挂 + unclean.leader.election.enable=true（是否可以从没有同步完全的副本当中选择新的leader为true） 从 OSR 中选 会丢数据
ISR 全挂 + unclean.leader.election.enable=false（是否可以从没有同步完全的副本当中选择新的leader为false） 分区不可用，等待原 Leader 恢复 不丢，但不可用

生产建议：unclean.leader.election.enable=false（默认值），宁可不可用也不丢数据。若业务允许丢数据换可用性（如日志采集），可设为 true，但必须明确告知业务方。

2.1 集群规模规划

2.1.1 节点数量

集群规模 Broker 数 ZooKeeper 数 适用场景
测试 1~3 1（可内嵌） 开发/测试
小型生产 3 3 日吞吐 < 1TB，可容忍单节点故障
中型生产 5~7 3 或 5 日吞吐 1~10TB
大型生产 9~20+ 5 日吞吐 > 10TB，核心业务
超大型 30+ 5（ZK 会成为瓶颈） 建议迁 KRaft

经验法则：

  • Broker 数 ≥ max(replication.factor, 3)，且建议为奇数（便于分布均衡）
  • ZooKeeper 集群 3 节点可容忍 1 台故障，5 节点可容忍 2 台；超过 7 台反而降低性能（写入需多数派确认）

第 12 章 集群扩容、缩容与迁移

扩容不是”加台机器就完事”。Kafka 扩容有三个动作：加 Broker → 数据重平衡 → 观察稳定。
其中”数据重平衡”是最容易出事的一步（限速、Leader 切换、磁盘打满）。

12.1 扩容前评估

12.1.1 判断是否真的需要扩容

指标 阈值 说明
磁盘使用率 > 70% 需要扩磁盘或扩节点
单 Broker 分区数 > 2000 元数据/句柄压力大，需扩节点
网络出口带宽 > 70% 线速 需加网卡或扩节点
CPU 使用率（Kafka 进程） 持续 > 70% 需扩节点
生产 P99 延迟 持续 > 100ms 先调优，再考虑扩容
副本同步延迟 持续增长 优先排查而非扩容

12.1.2 扩容方案对比

方案 操作 适用 风险
加 Broker 新节点入集群 + 分区重分配 吞吐/存储不足 重分配耗时长，需限速
加磁盘（同节点） log.dirs 加路径 + 重启 仅磁盘不足 需重启，且新盘不自动分担旧数据
加磁盘（扩分区） 云盘在线扩容 + xfs_growfs 云环境 无

14.4 容灾架构设计

14.4.1 方案一：同城双集群（推荐大多数场景）

要点：

  • MM2 单向即可，双向会引入循环复制（需 Topic 重命名策略）；

  • 定期演练切换（至少每季度一次）；
  • 消费位点同步依赖 Checkpoint Connector，务必开启。

14.4.2 方案二：双活（成本高，慎选）

复杂点：两个方向的同步会产生同名 Topic 冲突，需通过 replication.policy.class 做 Topic 重命名，或用 DefaultReplicationPolicy 加集群前缀。运维复杂度高，除非业务确实需要，否则不建议。

14.4.3 方案三：异地灾备（跨城）

要点：

  • 跨城带宽是瓶颈，必须限速 + 压缩；
  • 只同步核心 Topic，不是全量；
  • RPO 通常是分钟级（受带宽限制）；
  • 做好”异地集群容量不足”的预案（故障时业务量全部压过来）。

15.5 ZooKeeper 常见故障处理

15.5.1 ZK 单节点宕机

影响：若为 follower，集群仍可服务（多数派仍在），Kafka 无感知。若为 leader，触发 leader 重选举（通常几秒内完成）。

要点：ZK 的 follower 重启后会自动从 leader 同步，不需要手动干预。但如果宕机时间过长（超过快照+事务日志保留范围），需要全量同步，会消耗较多带宽/时间。

15.5.2 ZK 失去多数派（脑裂风险）

场景：3 节点 ZK 挂了 2 个，只剩 1 个。

处置（按优先级）：

  1. 尽快恢复至少 1 个节点，让多数派恢复（3 节点需要 2 个）；
  2. 若节点数据丢失，从备份恢复快照 + 事务日志；
  3. 绝不要通过修改 zoo.cfg 的 server 列表来”强行选主”——这会破坏 ZK 的一致性，可能导致数据分裂。

ZK 一致性公式：可用节点数 ≥ (总节点数 / 2) + 1。3 节点可挂 1 个，5 节点可挂 2 个。这就是 ZK 必须部署奇数的原因。

15.5.3 ZK 磁盘满

原因：快照与事务日志未清理（autopurge 未开启或失效）。

风险提示：删除事务日志前，确保至少有一个包含这些日志之前状态的快照还保留着。简单做法：保留时间上最新的快照 + 它之后的日志。

本章收录 15 个真实世界的典型事故。每一个都是血泪换来的。

案例 1：磁盘写满导致集群雪崩

项 内容
现象 3 台 Broker 中的 2 台磁盘 100%，随后所有生产者超时，业务全线告警
根因 某新上线的日志 Topic 未设置 retention.bytes，retention.ms 为 7 天，单日写入 2TB，磁盘 3 天写满
连锁反应 磁盘满 → Broker 无法写入 → 这些 Broker 上的 Leader 全部不可写 → ISR 收缩 → acks=all 的生产者全部阻塞 → 消息积压 → 内存 OOM
止血 ①立即缩短该 Topic 的 retention.ms 到 1 小时；②临时把 log.retention.check.interval.ms 调小到 60s 触发清理；③对积压的生产者降级
根治 ①所有 Topic 必须同时设置 retention.ms 和 retention.bytes；②建立磁盘容量预测模型（见 2.1）；③磁盘 70% 告警、85% 严重告警
预防 Topic 创建流程中加入”必须指定保留策略”的强制校验

案例 2：ISR 收缩 + acks=all 导致生产完全阻塞

项 内容
现象 业务方突然全部报”发送超时”，持续 20 分钟
时间线 14:02 一台 Broker 因磁盘 hang 掉线 → 14:03 其上分区 ISR 从 3 缩到 2 → 若有分区 ISR 缩到 1，min.insync.replicas=2 不满足 → 生产报 NotEnoughReplicasException
根因 ①Broker 磁盘 I/O hang（老 SATA 盘，await 200ms+）；②min.insync.replicas=2 与副本数 3 的组合下，一旦 ISR 缩到 1 就完全不可写
止血 ①强制重启故障 Broker（虽然会丢一点未刷盘数据）；②本次紧急将 min.insync.replicas 临时改为 1（有丢数据风险，需业务确认）
根治 ①更换 SSD；②副本数保持 3，min.insync.replicas=2 不改（可靠性优先）；③提高 replica.lag.time.max.ms 到 45s，减少误判导致的 ISR 收缩
预防 ①UnderReplicatedPartitions 立即告警；②磁盘 await > 20ms 告警

权衡思考：min.insync.replicas=2 是”可用性换可靠性”的典型。它的正确含义是：宁可不可写，也不接受可能丢数据的写入。如果业务不能接受不可写，就增加副本数（如 4 副本 + min.insync=2）。

案例 3：残留复制限速导致副本永远追不上

项 内容
现象 一次扩容后，UnderReplicatedPartitions 长期为 30 左右，持续 3 天不恢复
排查 Broker 都在线、磁盘正常、网络正常；最后在 kafka-configs.sh --describe --broker 2 中发现 follower.replication.throttled.rate=1048576（1MB/s）
根因 3 天前做分区迁移时设置了 1MB/s 限速（当时带宽紧张），迁移完成后忘记清除。此后所有副本同步都被限速在 1MB/s，1TB 的分区需要 11 天才能同步完
止血 清除所有 Broker 和 Topic 上的限速配置，副本在 15 分钟内全部追平
预防 ①把”清除限速”写进迁移 SOP 的最后一步；②限速配置纳入每日巡检（见附录 C 脚本）；③迁移脚本中加入 trap 保证退出时清限速

案例 4：ZK 会话超时导致 Broker 假死 + 大规模 Leader 切换

项 内容
现象 凌晨 3:00 突然出现大量 Leader 切换，持续 5 分钟，部分业务报”分区不可用”
根因 Broker 堆 8G，凌晨有日志清理 + 备份任务抢占 IO，导致一次 Full GC 停顿 22 秒 > zookeeper.session.timeout.ms=18000，ZK 判定 Broker 掉线，删除临时节点，Controller 触发其上 800 个分区的 Leader 重选举
止血 自动恢复（GC 结束后 Broker 重新注册，ISR 在 8 分钟内补齐）
根治 ①GC 参数改为 G1GC + MaxGCPauseMillis=200，Full GC 降到 1s 内；②zookeeper.session.timeout.ms 提到 30000（需同步调大 ZK 的 maxSessionTimeout）；③把 Kafka 数据盘与备份任务的盘分离
预防 ①监控 GC 停顿，超过 3s 告警；②Broker 所在机器不跑其他重 IO 任务；③OOMScoreAdjust=-500

案例 5：消费者 Rebalance 风暴

项 内容
现象 某消费组消费停滞 2 小时，LAG 从 0 涨到 800 万
根因 消费者 max.poll.interval.ms 用默认 300s，但单批 max.poll.records=2000，单批处理耗时高峰时超过 300s（下游 DB 慢查询），消费者被踢出组 → Rebalance → 重新分配 → 又超时 → 循环 Rebalance
止血 临时把 max.poll.records 从 2000 降到 100，立即恢复
根治 ①max.poll.records=200（与控制单批耗时）；②消费逻辑改为异步处理 + 水位控制；③优化下游慢查询
预防 ①监控日志中的 Rebalance 次数，超过阈值告警；②消费组上线前做压测，验证单批耗时

案例 7：分区迁移未限速导致网络打满

项 内容
现象 扩容迁移开始后 10 分钟，全部业务生产延迟从 20ms 飙到 5s
根因 迁移命令未加 --throttle，全速拷贝 15TB 数据，把万兆网卡打满

项 内容
现象 滚动升级 3.5 → 3.7，升完第 2 台后开始出现 UnsupportedVersionException，Topic 创建失败，部分分区元数据不一致
根因 升级二进制时未设置 inter.broker.protocol.version=3.5，导致 3.7 的 Broker 用新协议与 3.5 的 Broker 通信
止血 全部 Broker 回退到 3.5 二进制（幸好只升了 2 台）
根治 重新按正确流程升级：升级二进制时显式锁定 inter.broker.protocol.version，全部升级完成后再统一改版本
预防 ①把”锁定协议版本”写进升级 SOP 的必做项；②升级前在测试环境完整演练；③升级脚本中加入自动校验（检测 inter.broker.protocol.version 是否与集群当前版本一致）

案例 9：OOM Killer 杀死 Broker

项 内容
现象 Broker 进程”莫名消失”，无异常日志尾部
根因 Broker 堆 8G + PageCache 占用大量内存 + 同机部署了其他内存消耗型服务（如 ZK、监控 agent），宿主机内存耗尽，OOM Killer 按 OOM Score 杀掉了内存占用最大的 Kafka
止血 重启 Kafka（数据不会丢，多副本保障）

预防 ①巡检脚本检查 Topic 数量突增；②检查是否存在 ReplicationFactor=1 的 Topic（必须为 0）

16.1 事故预防的”十条军规”

  1. 所有 Topic 必须有明确的保留策略（retention.ms + retention.bytes）。

  7. Kafka 不与其他重 IO/内存型服务混部。
  8. 元数据每日备份，且每季度演练恢复。
  9. 高危命令（delete / reset-offsets / reassign / kill）纳入堡垒机审计 + 二次确认。
  10. 每次变更后 30 分钟内必须有人盯监控。

D.3 生产环境检查的”终极十问”

在集群上线前，用这十个问题自查：

  1. 副本数是 3 吗？min.insync.replicas 是 2 吗？acks 是 all 吗？unclean.leader.election.enable 是 false 吗？
  2. 每个 Topic 都有明确的 retention.ms 和 retention.bytes 吗？
  3. auto.create.topics.enable 和 delete.topic.enable 都关了吗？
  4. ZK 是 3 或 5 节点、独立部署、事务日志在独立盘吗？
  5. Kafka 与 ZK 是否混部？Kafka 是否与其他重 IO 服务混部？
  6. UnderReplicatedPartitions 有监控和告警吗？告警能到人吗？
  7. 磁盘 70%/85% 有分级告警吗？容量能撑多久算过吗？
  8. 元数据备份开启了吗？演练过恢复吗？
  9. 高危命令（delete/reset-offsets/reassign）有审计和二次确认吗？
  10. 上一次故障演练是什么时候？演练结果有记录吗？

如果这十个问题里有任何一个答案是”没有”，那么这个集群就还没到”生产就绪”。

结语

Kafka 的运维并不复杂，难的是细节的持续执行。

这套手册里 90% 的故障，根因都可以归纳为三类：

  1. 配置不当 —— 副本数、acks、min.insync.replicas、保留策略，这四个参数决定了 80% 的稳定性；
  2. 变更失控 —— 迁移不限速、升级不锁协议版本、限速不清除、高危命令无审计；
  3. 监控缺失 —— UnderReplicatedPartitions、磁盘水位、消费积压、GC 停顿，这四个指标能提前发现绝大多数问题。

真正的运维能力，不是”出事之后能修好”，而是”让事不发生”。

最后三条建议：

  • 把所有手工操作脚本化，脚本化的操作才能被 review、被复用、被新人执行；
  • 把所有假设验证化，”我以为没问题”是事故最常见的开场白；
  • 把每次故障文档化，本手册第 16 章的每一个案例，都是某个人某天凌晨的真实经历。

版本说明：本手册基于 Apache Kafka 3.0.x ~ 3.9.x（ZooKeeper 模式）编写。
ZooKeeper 将于 Kafka 4.0 起被移除，建议新集群评估 KRaft 模式，存量集群制定迁移计划（见 13.5）。
