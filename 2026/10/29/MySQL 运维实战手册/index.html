0.2 学习路线（建议 3~6 个月）

  1. 入门（1~2 周）：安装、SQL 基础、用户权限、字符集、基本备份恢复。
  2. 进阶（1~2 月）：InnoDB 原理、索引与 EXPLAIN、事务与锁、主从复制、慢日志分析。
  3. 精通（2~3 月）：高可用架构、监控体系、Online DDL、故障演练、性能调优、升级迁移。
  4. 专家：源码/内核机制、分布式架构选型、自动化平台建设。

0.3 运维黄金原则

  • 备份没有验证过，就等于没有备份。
  • 任何生产变更必须：可审核、可灰度、可回滚。
  • 先看监控和日志，再动手；先保护现场，再修复。
  • 删除/覆盖类操作前，先备份，再二次确认主机和库名。
  • 能用自动化做的事，不用手工做。

第 2 章 架构原理与 InnoDB 核心机制

2.1 逻辑架构

一条 SELECT 的过程：连接/认证 → 解析（词法/语法）→ 预处理 → 优化器选择执行计划（索引、join 顺序）→ 执行器调用引擎接口取数 → 返回。

2.2 InnoDB 内存与磁盘结构

组件 作用
Buffer Pool 缓存数据页，命中率决定读性能，一般设为物理内存的 50%~70%（专用机）
Redo Log 物理日志，保证持久性（WAL：先写日志再刷脏页）；崩溃恢复用
Undo Log 回滚与 MVCC 旧版本；长事务会让 undo 无法清理
Doublewrite 防止”页部分写”（torn page）
Change Buffer 缓存对非唯一二级索引的修改，减少随机 IO
Binlog（Server 层） 逻辑日志，用于复制和 PITR，不属于 InnoDB

2.3 一次更新的两阶段提交

两个”双 1”参数决定数据安全：

  • innodb_flush_log_at_trx_commit=1：每次提交刷 redo 到磁盘。
  • sync_binlog=1：每次提交刷 binlog 到磁盘。

追求极致性能可降级（如 2/0 或 sync_binlog=0），代价是宕机可能丢事务，核心业务不建议。

2.4 MVCC 与隔离级别

  • 每行有隐藏列：事务 ID（DB_TRX_ID）、回滚指针（DB_ROLL_PTR）。
  • 读视图（ReadView）决定哪个版本可见。
  • RC（读已提交）：每条语句生成 ReadView。
  • RR（可重复读，默认）：事务首次读生成 ReadView，整个事务沿用；配合间隙锁防幻读。

2.5 B+ 树索引与聚簇索引

  • InnoDB 表即索引：主键聚簇索引叶子节点存整行数据。
  • 二级索引叶子节点存主键值，查非覆盖字段需回表。
  • 主键应：短、单调递增、业务无关。

2.6 日志体系总览

日志 层级 用途 重点参数
error log Server 启动/运行异常 log_error、log_error_verbosity
slow log Server 慢 SQL slow_query_log、long_query_time
general log Server 全量 SQL（生产勿常开） general_log
binlog Server 复制、PITR log_bin、binlog_format
redo log InnoDB 崩溃恢复 innodb_redo_log_capacity
undo log InnoDB 回滚、MVCC innodb_undo_tablespaces

概念 说明
RPO 可容忍丢失的数据量（决定备份与 binlog 频率）

5.2 mysqldump（逻辑备份，小库首选）

参数说明

参数 含义
-ubackup -p 用 backup 账号登录，-p 表示交互式输入密码
--single-transaction 开启一个可重复读的一致性快照事务来导出，对 InnoDB 表不加表锁，备份期间业务可正常读写
--routines 导出存储过程和函数
--triggers 导出触发器（默认就是开启的，写出来只是更明确）
--events 导出事件调度器里的定时事件
--hex-blob 把 BINARY、VARBINARY、BLOB、BIT 等二进制列以十六进制（0x...）导出，避免字符集转换或转义造成数据损坏，代价是文件更大
--source-data=2 在备份文件里记录备份时刻的 binlog 文件名和位点；取值 2 以注释形式写入，取值 1 则写成可直接执行的 CHANGE REPLICATION SOURCE TO 语句

备份与恢复命令

--prepare 为什么必须做

热备期间数据在持续变化，数据文件被拷贝的时间点不一致，且可能有刚提交但还没刷盘的事务、写了一半的数据页。--prepare 本质上是模拟一次 MySQL 的崩溃恢复：

  • 前滚（redo）：把备份期间同步拷贝的 redo 日志重放到数据文件上，补齐先拷、后拷造成的差异，使所有文件统一到备份结束那一刻的状态。
  • 回滚（undo）：备份结束时尚未提交的事务，其修改需要回滚，避免留下半截事务。

执行完后，目录里的文件就是一份一致的、可直接启动的数据库。没有 prepare 的备份不能直接恢复。--prepare 只处理备份目录，不影响线上库，可在备份机上做。增量备份时，中间步骤必须带 --apply-log-only（只前滚、不回滚），因为后续增量里可能包含这些事务的提交记录，只有最后一步才执行回滚。

第 6 章 主从复制

6.1 复制原理

模式 特点
异步复制 默认，性能最好，主库宕机可能丢数据
半同步复制 至少一个从库收到 binlog 才返回，降低丢数据风险
组复制（MGR） 基于 Paxos 的多副本一致性，支持自动故障转移

6.2 基于 GTID 搭建主从（推荐）

原理：GTID（全局事务标识符）为每个已提交事务分配全局唯一编号，复制不再依赖”binlog 文件名 + 位点”，而是通过 SOURCE_AUTO_POSITION=1 自动协商同步点，天然避免位点错配、便于级联与切换。

前提（主从两端 my.cnf，见 3.1 模板；改后需重启实例生效）

从库建议配置 read_only=ON + super_read_only=ON，防止误写造成 GTID 冲突（见 6.5.1）；复制线程不受 read_only 限制。

生产建议限定来源网段 10.0.%，并启用 TLS（SOURCE_SSL=1）。

步骤 2：从库数据初始化（关键：同时写入正确的 gtid_purged）

gtid_purged 的含义：这些 GTID 对应的事务已包含在从库当前数据文件中，复制线程不需要再从主库拉取回放。数据初始化方式不同，gtid_purged 的写入方式也不同。

方式 A：mysqldump 逻辑备份（小库 / 跨版本首选）

  • --set-gtid-purged=ON（默认值）：导出文件头部会自动写入一条 SET @@GLOBAL.gtid_purged='<主库 gtid_executed 完整集合>';，导入从库时该语句自动执行，从库自动完成 gtid_purged 设置，无需人工干预。
  • ⚠️ 边界坑：若只导出部分库/表（不带 --all-databases），即使开启 --set-gtid-purged=ON，仍会写入主库全部 gtid_executed，从库会误以为主库所有事务都已执行而直接跳过，导致复制后丢数据。分库导出场景建议 --set-gtid-purged=OFF，再手动补 gtid_purged。
  • 若主库从未产生过 binlog 事务（gtid_executed 为空），导出文件不会生成该 SET gtid_purged 语句。

方式 B：Percona XtraBackup 物理备份（大库 / 生产主力，需手动设置）

物理恢复启动实例后不会自动设置 gtid_purged，需人工执行，且顺序不能颠倒：

  • 为什么必须这个顺序：SET GLOBAL gtid_purged 仅当 gtid_executed 为空时才允许执行，否则直接报错 GTID_PURGED can only be set when GTID_EXECUTED is empty。因此必须先 RESET BINARY LOGS AND GTIDS 清空本地 GTID 状态。
  • ⚠️ 反向操作是错的：先 SET gtid_purged 再 RESET，RESET 会清掉刚设好的 gtid_purged，复制链路直接失效。
  • 版本说明：RESET BINARY LOGS AND GTIDS 是新语法，用来取代 RESET MASTER；8.0 较早的小版本只支持 RESET MASTER，从哪个小版本开始支持新写法请以所用版本的官方手册为准。MySQL 8.4 已移除全部 MASTER/SLAVE 系列语法（含 RESET MASTER），生产一律使用 RESET BINARY LOGS AND GTIDS（本手册按 8.4 主线，故不再使用 RESET MASTER）。

6.6 主从切换（计划内）

  1. 确认从库延迟为 0，Executed_Gtid_Set 追平。

  4. 其他从库 CHANGE REPLICATION SOURCE TO SOURCE_HOST='新主'...（GTID 自动定位）。
  5. 切换 VIP/DNS/代理，旧主改为从库。

8.3 索引设计原则

  1. 最左前缀：联合索引 (a,b,c) 可用于 a、a,b、a,b,c，不能跳过 a。
  2. 等值在前，范围在后：范围列之后的列无法继续用于索引过滤。
  3. 区分度高的列靠前（需结合查询模式，不是绝对）。
  4. 覆盖索引：查询字段都在索引里，免回表。
  5. 排序/分组利用索引顺序，避免 filesort。
  6. 控制索引数量（单表一般 ≤5 个），写入成本随索引增加。
  7. 长字符串使用前缀索引或另做哈希/摘要列。
  8. 不在低基数列（如性别）单独建索引。

9.2 InnoDB 锁类型

  • 行锁：记录锁（Record）、间隙锁（Gap）、临键锁（Next-Key = Record + Gap，RR 下默认）。
  • 意向锁（IS/IX）：表级，协调表锁与行锁。
  • 表级锁：元数据锁 MDL、自增锁。
  • 锁是加在索引上的：无合适索引的 UPDATE/DELETE 可能锁住大量行甚至全表。

9.4 元数据锁（MDL）——DDL 卡死的元凶

现象：ALTER TABLE 卡在 Waiting for table metadata lock，随后所有对该表的查询排队，连接暴涨。

原因：有未提交的长事务或长查询持有表的共享 MDL。
处理：找到持锁会话（通常是 Sleep 状态却有未提交事务）→ KILL；预防：DDL 前检查长事务，设置 lock_wait_timeout 并在低峰执行。

9.5 死锁

死锁处理与预防

  • InnoDB 会自动检测并回滚代价较小的事务，应用必须捕获死锁错误（1213）并重试。
  • 多个事务按相同顺序访问表和行。
  • 事务尽量短小，不在事务中进行 RPC/用户交互。
  • 为更新条件建立合适索引，缩小加锁范围。
  • 考虑 RC 隔离级别，减少间隙锁。
  • 批量更新分批进行，避免一次锁定大量行。

通用原则：先止血，后定位；先保留现场，再重启；任何 kill / 重启 / 删除操作前确认影响面。

14.1 连接数暴涨 / Too many connections

排查方向：

  1. 是否有慢 SQL/锁/MDL 导致连接堆积（后果）还是应用连接泄漏（原因）；
  2. 按 user/host 分组定位来源；
  3. 止血：kill 堆积的会话、限制来源（MAX_USER_CONNECTIONS）、应用限流/重启连接池；
  4. 临时提高 max_connections（有内存上限，不是长久解法）；
  5. 预防：连接池配置、wait_timeout、慢 SQL 治理、告警。

14.2 CPU 使用率 100%

常见原因：大量全表扫描/无索引 JOIN、排序/临时表、突发并发、执行计划突变、统计信息过期。
处理：kill 问题 SQL → 紧急加索引（Online DDL）或 SQL 改写 → 限流 → 必要时 ANALYZE TABLE → 回归分析。

14.3 磁盘空间不足

占用源 处理
binlog 过多 确认所有从库已消费后 PURGE BINARY LOGS TO 'mysql-bin.000123'；调小 binlog_expire_logs_seconds
慢日志/general log 关闭 general log，轮转日志（logrotate + FLUSH LOGS）
临时文件/ibtmp1 查大排序/大临时表 SQL；重启才能释放 ibtmp1
undo 膨胀 先清理长事务，innodb_undo_log_truncate 生效
大表增长 归档/分区清理，OPTIMIZE/gh-ost 回收
备份文件放在数据盘 迁出

14.7 实例崩溃 / 无法启动

现象 可能原因 处理

14.8 大事务/回滚

大事务回滚耗时可能比执行更长。不要反复重启（重启后仍要继续回滚）；观察 information_schema.innodb_trx 的 trx_rows_modified 判断进度；长期预防是业务拆分批次。

14.9 Lost connection / Gone away

检查：wait_timeout 与连接池空闲回收是否匹配、max_allowed_packet 是否过小、网络设备（LB/防火墙）空闲超时、服务端是否重启（查看 Uptime）。

14.10 自增 ID 耗尽

INT 最大 21 亿，INT UNSIGNED 约 42 亿，到顶后插入报 Duplicate entry。预防：新表用 BIGINT UNSIGNED；老表提前在线改类型（gh-ost）并监控。

第 17 章 开发规范与运维规范

17.1 建表规范

  1. 必须使用 InnoDB + utf8mb4，表和字段必须有 COMMENT。
  2. 必须有主键，推荐自增 BIGINT UNSIGNED 或分布式有序 ID；主键与业务无关。
  3. 字段尽量 NOT NULL 并设默认值（NULL 影响索引与统计）。
  4. 禁止使用外键（由应用保证一致性）、触发器、存储过程（视团队约定）；谨慎使用视图。
  5. 单表索引不超过 5 个；联合索引不超过 5 列；索引命名 idx_、uk_。
  6. 避免大字段（TEXT/BLOB）放主表，可拆附表或对象存储。
  7. 必备审计字段：created_at、updated_at（可选 created_by）。
  8. 金额使用 DECIMAL 或整数分。
  9. 表名、字段名小写下划线，不使用保留字。

17.2 SQL 规范

  • 禁止 SELECT *；禁止无 WHERE 的 UPDATE/DELETE；
  • 禁止隐式类型转换、列上使用函数；
  • LIMIT 分页大偏移使用游标；
  • INSERT 必须显式列名；批量插入分批；
  • 事务要短小，避免事务内远程调用；
  • 超过 3 张表的 JOIN 需评审，JOIN 列类型/字符集一致；
  • 线上禁止 ORDER BY RAND()；
  • 统计类/大查询走只读从库或分析库。

17.3 运维操作规范

  • 生产操作必须双人复核（重要变更）；执行前复述”主机 + 实例 + 库表 + 动作”。
  • 禁止直接在主库做大批量更新/扫描；禁止在生产随意 FLUSH TABLES WITH READ LOCK。
  • 所有变更脚本入库留痕，保留回滚方案。
  • 权限分级：开发只读、线上变更走平台；DBA 账号带审计。
  • 值班制度、故障分级（P0~P3）、复盘模板（现象、影响、时间线、根因、改进项）。

  2. KILL 问题会话（先确认影响，事务回滚也需要时间）
  3. 加索引或改写 SQL（用 Online DDL，低峰执行）
  4. 主从切换（先确认从库数据已追平）
  5. 重启（最后手段，且必须先保存现场；大事务回滚中不要反复重启）

任何止血动作都要先说明影响，必要时请负责人确认。

20.7 第 4 步：根因分析与验证

  • 用时间线对齐：问题开始时间 ↔ 变更记录 ↔ 监控曲线变化点 ↔ 日志出现时间。
  • 用 5 Why 往下追：为什么连接满 → SQL 变慢 → 索引失效 → 发版后查询条件变了 → 发版前没有评审 SQL。
  • 验证根因：能否解释所有现象？测试环境能否复现？修复后现象是否消失？
  • 根因只是猜测时，复盘里写”待验证”，不要写成结论。

20.8 第 5 步：修复与复盘

  1. 永久修复（SQL、索引、参数、架构）也要走变更流程，不要直接在生产改。
  2. 写复盘（模板见 17.4）：现象、影响、时间线、根因、改进项（负责人与截止日期）。
  3. 把这次的排查方法固化成监控告警或脚本，下次提前发现。

20.9 排查经验

  • 先看监控曲线再敲命令：曲线能告诉你”什么时候开始变坏”。
  • 一次只改一个变量，否则无法判断哪个动作起了作用。
  • 别人说”没改过东西”不一定可信，以变更记录和日志为准。
  • 不确定时先问、先备份，不要赌。
  • 一个现象常有多个原因叠加，例如慢 SQL 导致连接堆积，同时备份又在抢 IO。
