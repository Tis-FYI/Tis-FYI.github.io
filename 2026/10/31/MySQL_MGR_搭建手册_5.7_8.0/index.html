1. MGR 简介与版本差异

MGR（MySQL Group Replication）是基于 Paxos 变种协议（XCom）的组复制插件，提供：

  • 高可用：多数派（majority）存活即可提供服务，自动故障检测与主节点选举
  • 数据强一致（可选）：基于认证（certification）的冲突检测，8.0 支持 group_replication_consistency
  • 自动成员管理：新节点加入自动通过分布式恢复追数据

1.1 版本差异对比

项目 MySQL 5.7 MySQL 8.0
最低版本 5.7.17 8.0.x 全系列（建议 ≥ 8.0.28）

复制通道命令 CHANGE MASTER TO ... FOR CHANNEL CHANGE MASTER TO（8.0.23+ 推荐 CHANGE REPLICATION SOURCE TO）

1.2 使用前提（硬性要求）

  • 所有表必须使用 InnoDB 引擎
  • 所有表必须有 主键（或非空唯一键）
  • 必须开启 GTID、binlog_format=ROW、log_slave_updates（8.0 为 log_replica_updates，默认 ON）
  • 网络延迟低且稳定，节点数建议为奇数（3/5/7）
  • 不支持复制过滤器（replication filters）用于 MGR 通道
  • 不建议使用外键级联、SERIALIZABLE 隔离级别（多主模式下尤其受限）
  • 事务大小限制：group_replication_transaction_size_limit（默认约 143MB）

gtid_executed 是 MySQL 中用来全局唯一标识并记录“当前节点已经执行并提交过的所有事务集合”的系统变量与状态集合。

GTID 构成：全局事务标识符（Global Transaction Identifier），格式为 source_id:transaction_id（例如 3E11FA47-71CA-11E1-9E33-C80AA9429562:1-5）。

存储与更新：

  • 内存中通过系统变量 @@global.gtid_executed 维护。
  • 持久化存储在系统表 mysql.gtid_executed 以及 Binary Log（二进制日志）中。
  • 无论是该节点自身作为 Primary 生成并提交的事务，还是作为副本/从节点从复制通道（或集群同步链路）接收并回放成功的外部事务，只要事务落盘提交，对应的 GTID 就会追加到 gtid_executed 集合中。

9.6 滚动升级（示例：8.0.x 小版本）

  1. 先升级 SECONDARY 节点：STOP GROUP_REPLICATION → 停库 → 替换二进制 → 启动 → START GROUP_REPLICATION
  2. 确认 ONLINE 后再升级下一个 SECONDARY
  3. 最后切换 PRIMARY：SELECT group_replication_set_as_primary('...')，再升级原 PRIMARY

5.7 → 8.0 升级需谨慎，不支持混合版本集群长期运行；建议新建 8.0 集群后迁移数据，或使用 MySQL Shell 的 util.checkForServerUpgrade() 做预检查。

13. 最佳实践与限制

13.1 最佳实践

  1. 节点数量：奇数，3 或 5 节点；跨机房时需考虑延迟（建议 RTT < 10ms，跨 AZ 可行，跨城需谨慎）
  2. 优先单主模式：避免多主冲突与 DDL 并发问题，除非业务确有多点写入需求并已充分压测
  3. 所有表必须有主键，避免大事务（单事务过大会导致延迟/被拒绝），批量操作分批提交
  4. 关闭 start_on_boot，在集群稳定、确认无数据差异的前提下，再考虑开启，防止异常节点自动加入引发问题
  5. sync_binlog=1 与 innodb_flush_log_at_trx_commit=1 保障数据安全
  6. 监控与告警：覆盖成员状态、延迟队列、流控触发次数、磁盘空间
  7. 一致性：8.0 对读一致性有要求的场景使用 group_replication_consistency=BEFORE_ON_PRIMARY_FAILOVER 或 AFTER（会增加延迟，需评估）
  8. 备份：在 SECONDARY 上做备份，定期演练恢复和新节点重建
  9. 版本一致：同一集群各节点使用相同 MySQL 版本；升级时按滚动升级流程，升级期间不要执行 DDL
  10. 网络：独立的内网网段承载 33061 通信，优先使用万兆/低延迟网络
  11. 时间同步：NTP/chrony，避免时钟漂移引起的异常判断

13.2 已知限制

  • 仅支持 InnoDB 引擎，所有表需主键
  • 不支持 SERIALIZABLE 隔离级别（多主模式下认证机制限制）
  • 多主模式下，对同一对象的并发 DDL 与 DML 可能导致数据不一致，官方不建议
  • 多主模式下外键级联操作存在冲突检测盲区，建议关闭外键级联
  • 最多 9 个成员
  • 不支持表锁（LOCK TABLES）和命名锁（GET_LOCK）的跨节点语义
  • 大事务受 group_replication_transaction_size_limit 限制
  • 复制过滤器不可用于 group_replication_applier 和 group_replication_recovery 通道

13.3 快速检查清单（上线前）

  • 三节点 server_id 唯一，server_uuid 唯一（克隆虚拟机时需删除 auto.cnf）
  • group_name 一致且为合法 UUID
  • /etc/hosts 或 DNS 解析正常，report_host 正确
  • 防火墙放行 3306 / 33061
  • GTID、ROW、binlog 已开启；5.7 binlog_checksum=NONE
  • 复制账号已创建，且创建时关闭了 binlog
  • 所有业务表均为 InnoDB 且有主键
  • 仅一个节点执行引导，引导后立即关闭 bootstrap_group
  • 故障切换、全组重启、节点重建流程已演练
  • 监控告警、备份策略已落地
