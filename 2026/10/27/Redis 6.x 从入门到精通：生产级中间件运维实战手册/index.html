第一章：初识 Redis 6.x —— 运维视角下的核心原理与 6.x 里程碑特性（入门篇）

很多刚接手 Redis 的运维同学都会有一个困惑：“大家都说 Redis 是单线程的，为什么 Redis 6.0 又吹嘘自己引入了多线程？到底需不需要配多核 CPU？”

1.1 用“餐厅大厨与传菜员”秒懂 Redis 6.x 的线程模型

要想在排障时不抓瞎，先记住一句话：Redis 6.x 的“核心命令执行（做菜）”依然是单线程的，但把最耗时费力的“网络数据包读写（迎宾点菜与端菜）”以及“大垃圾清理（洗碗）”交给了多个后台线程并行处理！

  • 运维核心启示：
    1. 为什么单条慢命令依然会卡死整个 Redis？ 因为真正操作内存数据库的“大厨（主线程）”永远只有 1 个！如果研发发了一条 KEYS * 或者对包含 500 万个元素的 Hash 执行 HGETALL，主线程被霸占 3 秒，这 3 秒内其他所有客户端的读写请求都会超时排队！
    2. 服务器需要几核 CPU？ 哪怕是 1 个 Redis 实例，也建议至少分配 4~8 核 CPU：1 核给主线程跑满、2~4 核分给 6.x 的多线程网络 I/O、剩下的核留给 bgsave / bgrewriteaof 的 fork 子进程和后台 BIO 线程，防止持久化时跟主线程抢同一个 CPU 核。

1.2 运维必须懂的 5 大基础数据类型与“底层编码膨胀拐点”

研发只关心怎么调 SET、HSET，但运维必须知道它们在内存里长什么样——因为同样存 1000 万条数据，懂底层编码的用法只需 1GB 内存，不懂的用法要吃掉 8GB 内存！

对外数据类型 典型业务场景 底层紧凑编码（小数据时极省内存） 底层标准编码（大数据时自动转换） 运维必须关注的“内存膨胀拐点”与治理准则
String（字符串） 缓存 JSON、分布式锁、计数器 int（纯数字）
embstr（<= 44 字节短字符串，连续内存分配）		 raw（> 44 字节动态字符串 SDS） 大量零散的小 String Key 会因为每個 Key 都有 redisObject 元数据头而浪费极多内存，海量小 KV 建议改用 Hash 分桶存储。
Hash（哈希字典） 用户信息、购物车、商品属性 ziplist（压缩列表，连续内存无指针开销） hashtable（哈希表，查询 $O(1)$ 但指针内存开销大） 当 Hash 的字段数超过 hash-max-ziplist-entries（默认 512）或任意 Value 长度超过 hash-max-ziplist-value（默认 64 字节）时，会瞬间膨胀转换为 hashtable，内存占用翻数倍！

1.3 Redis 6.x 里程碑级运维新特性全景

相比于老旧的 Redis 3.x / 4.x / 5.x，Redis 6.x（尤其是生产最稳定的 6.2 LTS） 为运维带来了四大刚需特性：

  1. ACL（Access Control Lists）细粒度权限控制：在 6.0 之前，Redis 只有一个全局密码 requirepass，只要拿到密码就能执行 FLUSHALL 删库！6.0 引入了类似 MySQL 的多用户权限体系，可以给不同微服务分配不同账号，限制它只能访问特定前缀的 Key（如 ~order:*），并且从根源上禁止执行 @dangerous 高危命令集。
  2. 多线程网络 I/O（Threaded I/O）：在万兆网卡、高并发小包读写场景下，开启 4 个 I/O 线程即可让单实例 QPS 从 10 万+ 轻松突破到 20 万 ~ 30 万+。
  3. 过期淘汰算法与 Lazy Free 全面增强：在 6.x 中，不仅手动删除可以用 UNLINK 异步释放，连主从全量同步清空旧库、过期 Key 自动驱逐、覆盖已有大 Key 都可以交由后台线程异步销毁，彻底告别删除大 Key 引起的卡顿。
  4. 原生支持 SSL/TLS 加密通信与无盘复制（Diskless Replication）成熟化：支持云上跨可用区安全加密传输，且主从复制可以直接通过网络 Socket 发送 RDB 数据流，无需先写主库磁盘。

第二章：生产级容量规划、OS 内核调优与标准化部署（入门到实战）

2.1 硬件选型与单实例容量黄金法则

运维铁律：为什么单个 Redis 实例的内存上限绝对不要超过 10GB ~ 16GB？

很多公司买了一台 128GB 内存的服务器，直接在上面起了一个 maxmemory 100gb 的单实例 Redis。结果一到凌晨做 RDB 备份或者从库重连全量同步，整台服务器直接卡死甚至触发 Linux OOM Killer 把 Redis 进程强杀了！

核心根因：fork() 与写时复制（Copy-on-Write, CoW）机制

  1. 当 Redis 执行 bgsave（生成 RDB）或 bgrewriteaof（重写 AOF）时，主线程必须调用操作系统的 fork() 函数创建一个子进程。
  2. 第一道坎（fork 本身的阻塞时间与实例内存成正比）：fork() 虽然不需要拷贝物理内存里的数据，但它必须复制主进程的内存页表（Page Table）！在复制页表期间，Redis 主线程是完全阻塞停止响应的。
    • 实测经验：10GB 的实例，fork 大约耗时 20ms ~ 50ms；如果实例高达 60GB，特别是在虚拟机/云主机（Xen/KVM）上，fork 一次可能直接卡死主线程 1 秒 ~ 3 秒！
  3. 第二道坎（写时复制 CoW 导致物理内存翻倍膨胀）：fork 出来的子进程正在慢吞吞地把 60GB 数据往磁盘上写（耗时可能长达 3 分钟）。在这 3 分钟内，如果线上写请求非常猛，把主进程里 50% 的数据都修改了一遍，操作系统就会把这些被修改的内存页全部复制一份新的（Copy-on-Write）！这就意味着：60GB 的实例在持久化期间，最高需要额外消耗 30GB~60GB 的物理内存！

生产容量规划黄金公式

  • 单实例内存规格（maxmemory）：强烈建议控制在 8GB ~ 16GB 以内（小实例 fork 极快、主从全量同步秒级完成、故障影响面小）。如果服务器有 128GB 内存，请采用 Redis Cluster 多实例部署（如一台机器跑 4~6 个 16GB 的实例，绑定不同端口）。

  • 机器物理内存预留比例：

    • 所有 Redis 实例的 maxmemory 总和小于物理机总内存65%
    • 为什么必须预留 35% 以上的空闲物理内存？ 这 35% 是专门留给 fork() 写时复制（CoW）内存膨胀、主从复制缓冲区（Replication Buffer）、AOF 重写缓冲区以及操作系统自身开销的保命空间！

第三章：数据持久化机制深度解析：RDB、AOF 与混合持久化（中级篇）

很多运维在被问到“Redis 挂了重启会丢多少数据？为什么重启加载要半个小时？”时答不上来，根源在于没摸透 RDB 和 AOF 的脾气。

3.1 RDB、AOF 与混合持久化全方位对比

维度 RDB（内存快照） 纯 AOF（追加写命令日志） RDB + AOF 混合持久化（Redis 4.0+/6.x 默认开启）
通俗比喻 给内存拍一张压缩数码照片（二进制紧凑格式）。 记账本，把你执行过的每一条写命令（SET k v）原封不动记下来。 先拍一张数码照片，照片拍完之后的新变动继续记账。
文件体积 极小（经过 LZF 压缩，通常只有内存大小的 30%~50%）。 极大（哪怕定期 Rewrite 重写，依然比 RDB 大几倍）。 适中（兼顾了 RDB 的高压缩率）。
宕机丢数据窗口 丢分钟级数据（比如每隔 5~15 分钟才拍一次快照，中间宕机全丢）。 最多丢 1 秒数据（默认 appendfsync everysec 每秒刷盘一次）。 最多丢 1 秒数据（增量部分依然每秒刷盘）。
重启恢复速度 极快（直接把二进制块读进内存，10GB 数据约需 10~30 秒）。 极慢（要把几千万条命令从头到尾重新执行一遍，10GB 可能要 20 分钟）。 极快（绝大部分数据按 RDB 二进制秒级加载，只重放最后一点增量 AOF）。
生产环境选型建议 适合纯缓存业务，或作为每日异地冷备份文件。 不建议单独使用旧版纯文本 AOF。 核心业务生产环境唯一推荐标配QQ。

运维防坑必知：如果我在线开启了 AOF，重启时 Redis 到底读哪个文件？
只要 appendonly yes 开启，Redis 重启时永远只认 AOF 文件，完全忽略 dump.rdb！
千万别踩这个删库大坑：假设你线上跑了半年一直只开了 RDB（有 10GB 数据），没开 AOF。如果某天你直接去改 redis.conf 把 appendonly 改成 yes，然后直接重启 Redis——因为磁盘上生成的 appendonly.aof 是个 0 字节的空文件，Redis 启动后只加载这个空 AOF，内存里 10GB 数据瞬间被清空（而且下一次 bgsave 还会用空内存把你原本完好的 dump.rdb 覆盖掉）！

4.2 运维每日巡检必看：INFO 核心指标解读速查表

登录 Redis 执行 INFO（或按模块查 INFO memory、INFO stats、INFO replication），重点关注以下黄金指标：

所属模块 指标名称 物理含义通俗解读 健康标准与排障指向
Clients connected_clients 当前已连接的客户端数量。 若逼近 maxclients（如 > 8000），需执行 CLIENT LIST 排查哪个应用连接池泄漏。
Clients blocked_clients 正在被阻塞等待的客户端数（如执行了 BLPOP / BRPOP）。 非阻塞队列业务应为 0。
Memory used_memory_human Redis 分配器（jemalloc）实际用来存数据、内部缓冲区的内存总量。 不可长期贴近 maxmemory（建议日常 < 80%）。
Memory used_memory_rss_human 从 Linux 操作系统角度看，Redis 进程占用的实际物理内存（Resident Set Size）。 rss 通常比 used_memory 略大一点（包含内存碎片）。
Memory mem_fragmentation_ratio 内存碎片率（等于 used_memory_rss / used_memory）。 1.0 ~ 1.4 为健康。
• > 1.5：碎片严重，浪费物理内存，开启 CONFIG SET activedefrag yes。
• < 1.0：极度危险！ 说明物理内存不够，部分 Redis 内存已经被操作系统换出到了磁盘 Swap 上，此时性能会暴跌百倍！
Stats instantaneous_ops_per_sec 当前实时的每秒执行命令数（QPS）。 配合 CPU 使用率评估单机水位（单线程通常 5万~8万 QPS，开启多线程可达 15万+）。
Stats rejected_connections 因超过 maxclients 而被拒绝的连接总数。 正常必须为 0。大于 0 说明发生过连接池打满故障。
Stats evicted_keys 因内存达到 maxmemory 上限而被强制淘汰踢出的 Key 总数。 若持续暴增，说明内存容量不足或业务写入了大量未设过期时间的垃圾数据。
Stats keyspace_hits / keyspace_misses 缓存命中次数 / 未命中次数。 缓存命中率 = $\frac{\text{hits}}{\text{hits} + \text{misses}}$，健康缓存业务应 > 90%；若突然暴跌，需警惕缓存穿透攻击。
Replication master_link_status（从库看） 从库与主库的复制连接状态。 必须为 up。若为 down，说明主从失联正在重连。
Persistence latest_fork_usec 上一次执行 fork() 耗费的微秒数！ < 50000（50毫秒）为健康。若高达几十万微秒（几百毫秒），说明实例太大或未关闭透明大页 THP！

第五章：高可用与分布式集群架构实战：主从、哨兵（Sentinel）与 Cluster（进阶篇）

5.1 三大生产架构选型对比

架构模式 核心组成 解决什么问题？ 容量上限 适用业务场景
主从复制（Master-Replica） 1 主 + N 从 数据多副本冗余、读写分离。 单机内存上限（建议 <= 16GB） 仅用于测试或非核心边缘业务（主库挂了无法自动切换，需人工干预）。
哨兵模式（Redis Sentinel） 1 主 + 2 从 + 3 哨兵进程 自动故障转移（高可用 HA）：主库宕机后哨兵自动投票把从库提升为新主库，并通知客户端。 单机内存上限（建议 <= 16GB） 数据量在 16GB 以内的中小型核心业务；支持所有多 Key 命令与事务，无需考虑槽位限制。
分片集群（Redis Cluster） 至少 3 主 + 3 从（共 6 个实例，内置 Gossip 协议与 16384 哈希槽） 水平扩容（海量内存 + 超高并发） + 自动高可用：数据自动打散到多个主节点，无需额外部署哨兵。 TB 级（官方支持最高 1000 个节点，生产建议单集群 <= 200 节点） 数据量 > 16GB 或 QPS > 10万 的大型高并发生产环境。

5.2 主从复制最致命的坑：“无限全量同步风暴”原理解析与根治

（1）主从复制是怎么工作的？

  1. 全量同步（Full Resynchronization）：从库第一次连上主库时，主库执行 bgsave 生成 RDB 文件发给从库，同时把生成 RDB 期间新收到的写命令存在内存的 client-output-buffer-limit replica（从库复制输出缓冲区） 里，等从库加载完 RDB 再发过去。
  2. 增量同步（Partial Resynchronization，PSYNC）：平时网络难免会闪断一两秒。为了避免网络一抖就重新传十几个 GB 的 RDB，主库在内存里维护了一个固定大小的环形数组，叫做 repl-backlog-size（复制积压缓冲区）。从库断连重连后，上报自己断开前的偏移量（offset），只要这个 offset 还在主库的环形缓冲区里没被覆盖掉，主库就只把断连期间漏掉的那几 MB 命令发给从库即可！

（2）两大死亡螺旋（运维必考排障题）

  • 死亡螺旋 A：环形积压缓冲区 repl-backlog-size 太小导致抖动变全量
    • 现象：主库默认 repl-backlog-size 只有区区 1MB！线上高峰期每秒写入 10MB 数据，主从网络哪怕只闪断 0.2 秒，这 1MB 环形缓冲区就全被新数据覆盖了。从库重连后发现 offset 找不到了，被迫触发全量同步！
    • 根治公式：$$\text{repl-backlog-size} \ge 2 \times \text{峰值每秒写入字节数} \times \text{最大容忍网络闪断秒数}$$（生产建议直接配 256mb ~ 512mb）。
  • 死亡螺旋 B：复制输出缓冲区 client-output-buffer-limit replica 溢出导致无限重连死循环
    • 现象：从库触发了全量同步，主库花了 2 分钟生成并发送 15GB 的 RDB，从库又花了 2 分钟清空旧内存并加载 RDB。在这整整 4 分钟里，主库新收到的所有写命令全部积压在主库内存的 replica output buffer 中。一旦积压超过默认的 256mb（或持续 60 秒超过 64mb），主库会直接强制掐断该从库的连接！ 1 秒后从库再次重连，再次请求全量同步，再次撑爆断开——主库陷入无限 fork 死循环，CPU 和网卡彻底打爆！
    • 根治方案：① 控制单实例内存 <= 16GB；② 调大配置：CONFIG SET client-output-buffer-limit "replica 512mb 128mb 60"。

第六章：内存管理、过期淘汰策略与 BigKey / HotKey 治理（进阶篇）

6.1 为什么 Key 明明已经过期了，Redis 内存却没有降下来？

这是业务方最爱质问运维的问题：“我给 Key 设了 1 小时过期，现在早过了 1 小时了，为什么监控上 Redis 内存还占着 8GB 没降？”

搞懂 Redis 的“惰性删除 + 定期采样删除”双引擎

Redis 绝对不会为几千万个 Key 分别启动一个定时器（那会把 CPU 直接烧穿），而是采用以下两种轻量策略：

  1. 惰性删除（Lazy Expire）：当客户端再次来访问（如 GET key）某个 Key 时，Redis 顺手检查一下它有没有过期，如果过期了当场删掉并返回空。但如果这批过期的 Key 再也没有人去查它呢？它就会一直赖在内存里！
  2. 定期随机采样删除（Active Expire）：Redis 默认每秒执行 10 次（由 hz 10 控制）后台巡检：
    • 每次从设置了过期时间的字典中随机抽取 20 个 Key；
    • 删掉这 20 个里面已经过期的 Key；
    • 如果发现这 20 个里面有**超过 25%（即 >= 5 个）**已经过期了，立刻再抽 20 个继续删，直到过期比例低于 25% 或单次耗时超过 25ms 为止。
  • 运维调优手段：如果业务写入了海量短期过期的 Key 且不再访问，导致过期 Key 清理跟不上写入速度，可以在线将 hz 调大到 20 ~ 50（或开启 Redis 6.x 的 dynamic-hz yes），或者开启主动驱逐努力程度 CONFIG SET active-expire-effort 3（默认 1，范围 1~10）。

6.2 8 种 maxmemory-policy 内存淘汰策略怎么选？

当内存真正顶到 maxmemory 天花板时，Redis 会触发内存淘汰策略。生产环境选错这个参数，会导致分布式锁被意外踢掉或写入直接报错：

策略分类 淘汰策略名称 具体行为解读 生产推荐指数与适用场景
不淘汰 noeviction（默认） 内存满了之后不踢任何 Key，所有写请求（SET/LPUSH）直接报错 OOM command not allowed，读请求和 DEL 正常。 仅用于把 Redis 当作纯数据库/消息队列/分布式锁专库，绝对不允许丢任何数据的场景。
在所有 Key 中淘汰 allkeys-lfu 在所有 Key（无论设没设过期时间）中，淘汰**访问频率最低（Least Frequently Used）**的 Key。 ⭐⭐⭐⭐⭐ Redis 4.0+/6.x 纯缓存场景首选！比 LRU 更聪明，能防止偶发性全表批量扫描把真正的热点缓存冲刷掉。
在所有 Key 中淘汰 allkeys-lru 在所有 Key 中，淘汰**最久未访问（Least Recently Used）**的 Key。 ⭐⭐⭐⭐ 经典纯缓存场景标配（即使研发忘了设置 TTL 也不会把内存撑死报错）。
在所有 Key 中淘汰 allkeys-random 在所有 Key 中随机抓一个踢掉。 不推荐。
仅在设了 TTL 的 Key 中淘汰 volatile-lfu / volatile-lru 只会在设置了过期时间（TTL）的 Key 中按 LFU / LRU 淘汰；凡是没设过期时间的持久 Key 绝对不碰！ ⭐⭐⭐⭐⭐ 混合业务场景首选！比如同一个 Redis 里既存了不能丢的配置/分布式锁（不设 TTL），又存了普通缓存（设了 TTL）。
仅在设了 TTL 的 Key 中淘汰 volatile-ttl 在设了 TTL 的 Key 中，挑剩余寿命最短（最快要过期）的先踢掉。 适合明确按过期时间决定缓存价值的场景。
仅在设了 TTL 的 Key 中淘汰 volatile-random 在设了 TTL 的 Key 中随机踢。 不推荐。

6.3 BigKey（大 Key）扫描、危害剖析与无损清理 SOP

（1）到底多大才算 BigKey（大 Key）？

在运维标准中，不要以为 100MB 才叫大 Key！只要满足以下任一条件，就属于生产需要治理的 BigKey：

  • String 类型：单个 Value 大小超过 10KB（超过 1MB 属于严重高危大 Key）。
  • 集合类型（Hash / List / Set / ZSet）：包含的元素个数超过 5000 个（或总体积超过 10MB）。

（2）BigKey 的四大夺命危害

  1. 网卡流量打满与客户端超时：一个 2MB 的 String Key，每秒被并发读取 1000 次，瞬间就会产生 2GB/s（16Gbps） 的出向流量，直接把万兆网卡打死！
  2. 主线程严重阻塞：对包含 10 万个字段的 Hash 执行一次 HGETALL，主线程会被卡死数百毫秒，所有其他请求全部排队。
  3. Redis Cluster 严重的内存倾斜：在分片集群中，同一个大 Key（如 2GB 的大 Hash）永远只能落在某 1 个分片节点上，导致这台节点内存爆满触发 OOM，而其他 9 台节点内存空空如也。
  4. 删除时引发主从雪崩：在未开启 Lazy Free 时，直接执行 DEL bigkey 释放上百万个链表节点，主线程会直接卡死数秒，甚至触发哨兵/集群误判主库宕机发生主从切换！

（3）在线安全扫描与无损删除 BigKey 实战

根治方案（推动研发改造）：对于几十万元素的超大 Hash/Set，推动研发按照固定取模（如 hash_key:0 ~ hash_key:99，通过 field_id % 100 路由）拆分成 100 个小 Hash；查询时严禁使用 HGETALL / SMEMBERS，必须改用渐进式遍历 HSCAN / SSCAN / ZSCAN。

6.4 HotKey（热 Key）实时发现与治理

（1）什么是 HotKey？

某个 Key（例如某顶流明星官宣微博、秒杀爆款商品库存 sku:8888）在瞬间承受了每秒 数万次甚至几十万次 的访问。即使你是 100 台节点的 Redis Cluster，因为同一个 Key 固定映射到同一个槽位，这几十万 QPS 会全部砸在同一台分片主节点上，瞬间将该节点单核 CPU 打到 100%！

（2）如何在线抓出 HotKey？

⚠️ 运维生死红线警告：生产高并发故障期间，严禁贸然执行 redis-cli MONITOR！
很多教程教你用 MONITOR 抓热 Key。但在每秒 10 万 QPS 的生产主库上，一旦敲下 MONITOR，Redis 会把所有命令复制一份塞进该连接的内存输出缓冲区，单次 MONITOR 会直接让 Redis 吞吐量暴跌 50% 以上，并在几秒钟内撑爆几个 GB 的内存导致 OOM 宕机！ 如万不得已必须抓一瞬间的命令，只能用 timeout 1s redis-cli MONITOR | head -n 500 > /tmp/mon.txt 严格限时 1 秒立即退出！

（3）HotKey 生产治理三板斧

  1. 客户端本地二级缓存（最彻底）：利用 Caffeine / Guava Cache（或配合 Redis 6.0 原生 Client-side Caching 客户端缓存广播机制），将热 Key 缓存在应用服务器本地 JVM 内存中 3~5 秒，挡住 99% 的读流量。
  2. 热 Key 多副本分片打散：对于只读热 Key，在写入时同时冗余写入多个带随机后缀的 Key（如 hotkey#1、hotkey#2 … hotkey#10），让它们散列到 Redis Cluster 的 10 台不同机器上，客户端读取时随机挑一个后缀读。

② 高可用架构：部署 Redis Cluster 跨机架/跨可用区多副本容灾。

事故四：Redis Cluster 集群状态变成 cluster_state:fail，全集群报错 CLUSTERDOWN The cluster is down

当你执行 CLUSTER INFO 看到 cluster_state:fail 时，只有两种可能原因：

  • 原因 1：有某个主分片和它的所有从分片同时挂了，导致那一部分哈希槽（Slots）无人负责（cluster_slots_ok < 16384）

    • 标准恢复：找到挂掉的那组主从节点，把它们重新启动拉起来，集群会自动恢复 ok。
    • 极端兜底（主从机器硬盘全部彻底损坏无法找回数据，但老板要求剩余 90% 的健康节点必须先恢复对外服务）：
      1. 临时将所有存活节点的 cluster-require-full-coverage 从默认的 yes 改为 no（允许槽位不全时存活节点继续正常提供服务）：
      2. 使用 redis-cli -a '密码' --cluster fix <存活节点IP:Port> 修复孤立槽位，将其强制分配给存活的主节点。

事故六：客户端报大量 MOVED 或 ASK 重定向，或者集群 pipeline 报错 CROSSSLOT Keys in request don't hash to the same slot

  • 根因剖析：业务从单机/哨兵模式迁移到 Redis Cluster 后，代码里使用了 MGET k1 k2 k3、事务 MULTI/EXEC 或 Lua 脚本操作多个 Key。在 Cluster 中，不同 Key 算出来的哈希槽落在不同机器上，默认严禁跨槽位执行多 Key 命令！
  • 解决方案：
    1. 如果这批 Key 在业务上强相关（例如同一个用户 user_10086 的基本资料、订单、积分），让研发使用 Hash Tag（大括号语法 {...}）：把 Key 命名为 {user_10086}:profile、{user_10086}:orders。Redis Cluster 计算 CRC16 时只计算大括号 {} 里面的字符串，保证它们 100% 落在同一个哈希槽上！
    2. 运维必须警惕的 Hash Tag 副作用：督促研发绝对不能把固定常量放进大括号里（比如写成 {prod_env}:order_1、{prod_env}:order_2），否则全公司几千万个 Key 都会被强制塞进同一个槽位，直接把那一台分片节点撑死！
