第一章：初识 Kubernetes —— 运维视角下的集群架构与请求全生命周期（入门篇）

很多传统运维刚转 K8s 时，会被一堆 apiserver、controller、kubelet、cni 搞得头晕眼花。其实，你只需要把整个 K8s 集群想象成一个全自动化的“现代化集装箱港口调度中心”。

1.1 用“集装箱港口调度中心”秒懂 K8s 核心组件

一个生产级 K8s 集群由两类服务器组成：控制平面节点（Control Plane / Master 节点，只当指挥官不跑业务） 和 工作节点（Worker Node，真正干苦力跑业务容器的货轮）。

所在节点 组件名称 港口角色比喻 真实职责大白话解读 运维生死红线（挂了会怎样？）
Master 控制面 kube-apiserver 唯一前台总机 / 安检大门 集群里唯一能直接读写 etcd 数据库的组件！不管是运维敲 kubectl，还是其他组件汇报状态，都必须先过它的认证（Authentication）、鉴权（RBAC）和准入控制（Admission）。 无状态组件，可通过负载均衡器（HAProxy/Nginx + Keepalived）部署 3 台实现高可用。全部挂掉时：已有业务容器照常运行，但无法发布、扩缩容或查询状态。
Master 控制面 etcd 唯一保险柜总账本 强一致性的分布式 KV 数据库（基于 Raft 协议）。集群里所有的配置、Pod 状态、Secret 密码全存在这里。 全集群最娇贵的心脏！ 必须部署 3 台或 5 台（奇数） 且必须挂载 SSD 固态盘；一旦超过半数节点损坏且无快照备份，整个 K8s 集群直接脑死亡！
Master 控制面 kube-scheduler 智能调度排班员 专门盯着那些刚创建出来、还没分配机器（nodeName 为空）的新 Pod，经过两轮筛选——预选（过滤掉内存不够、有污点的机器） 和 优选（给剩余机器打分），拍板决定把 Pod 放到哪台 Worker 节点上。 只负责“拍板写账本（把选好的节点名写回 APIServer）”，自己绝不去启动容器。
Master 控制面 kube-controller-manager 24小时巡检纠偏大管家 内部包含几十个死循环控制器（Deployment、Node、Endpoint 控制器等）。它的唯一哲学就是：对比“账本里的期望状态（如 replicas: 3）”和“实际存活状态（如只剩 2 个）”，一旦不一致就立刻下单补齐！ 支撑 K8s 故障自愈的核心大脑（主备 Leader 选举模式运行）。
Worker 工作节点 kubelet 驻船包工头 跑在每一台宿主机上的 Linux systemd 服务（不跑在容器里）。它时刻监听 APIServer：“有没有分给我们这台机器的 Pod？” 一旦有，立刻指挥本机的容器运行时拉镜像、启容器、挂存储卷，并按时执行健康检查探针。 如果某台机器上的 kubelet 挂了超过 40 秒，Master 就会把这台机器标记为 NotReady，5 分钟后自动把上面的 Pod 驱逐重建到其他健康机器上！
Worker 工作节点 containerd 起重机操作工（容器运行时） 以前是 Docker，从 K8s 1.24 起正式移除内置 dockershim，全面采用更轻量的 containerd 调用底层 runc 真正创建隔离的 Linux 容器进程。 负责镜像拉取、容器生命周期管理。
Worker 工作节点 kube-proxy 船上内部电话交换机 每台节点跑一个（DaemonSet），负责把访问 Service 虚拟 IP（ClusterIP）的流量，通过内核的 iptables 或 IPVS 规则负载均衡转发给后端真实的 Pod IP。 如果某台节点的 kube-proxy 挂了，该节点上新发布的 Service 转发规则将无法更新。

1.2 为什么 K8s 的最小调度单位是 Pod，而不是单个容器？

新手最爱问：“Docker 已经能跑容器了，K8s 为什么还要在容器外面再包一层叫 Pod（豆荚） 的壳？”

用“合租一居室”秒懂 Pod 与 pause（Infra）根容器

假设你的主业务容器是一个轻量级的 Nginx 或 Java 程序，现在你想给它配一个日志采集器（Filebeat）或者流量代理（Envoy Sidecar）。

  • 如果把它们作为两个完全独立的容器去调度：它们可能被分到两台不同的物理机上，既没法直接通过 127.0.0.1 高速通信，也没法共享同一个本地日志目录。
  • Pod 的天才设计：
    1. 每当 Kubelet 启动一个 Pod 时，它会永远先启动一个体积极小（仅几百 KB）、什么业务都不干的隐藏容器——叫做 pause（又名 Infra 根容器）！
    2. 这个 pause 容器负责把“房间”租下来：申请到整个 Pod 唯一的 Pod IP，建好独立的网络命名空间（Network Namespace）和存储卷。
    3. 随后启动的业务容器 A（如 Java）和辅助容器 B（Sidecar 如 Filebeat），通过 Linux 内核技术直接 Join 加入 pause 容器的网络命名空间！
    4. 最终效果：同一个 Pod 里的所有容器，看到的网卡、IP 地址、端口范围完全是同一个（可以直接通过 localhost:8080 互相访问，但要注意不能监听同一个端口！），并且只要 pause 容器不死，哪怕里面的业务容器崩溃重启了十次，这个 Pod 的 IP 地址也不会发生改变！

第二章：生产级集群规划、OS 内核调优与高可用部署基线（入门到实战）

2.1 生产集群容量与网段规划黄金铁律

在动手装集群前，以下 3 个规划一旦上线极难修改，必须提前算清：

  1. 三大核心网段（CIDR）绝对不能重叠，且必须留足扩容余量！
    • 宿主机物理网段（Node CIDR）：如 10.10.0.0/16。
    • Pod 虚拟网段（Pod CIDR）：推荐 10.244.0.0/16 或 172.16.0.0/16（默认每台宿主机分一个 /24 子网，即每台节点最多可分 254 个 Pod IP；单节点默认硬限制 maxPods: 110）。
    • Service 虚拟网段（Service CIDR）：推荐 10.96.0.0/12（切勿配成 /24，否则全集群建满 254 个 Service 就报 IP 耗尽！）。
  2. Etcd 与控制面节点规划：
    • 生产环境严禁单 Master 裸奔！必须部署 3 台（可承受挂 1 台）或 5 台（可承受挂 2 台） 控制面节点。
    • 千万别选 2 台或 4 台偶数节点！ 因为 Raft 协议要求多数派 $\lfloor N/2 \rfloor + 1$ 存活：2 台挂 1 台就剩 1 台（$<2$，整个集群只读瘫痪），容灾能力甚至不如 1 台！
    • 集群规模超过 50 个 Worker 节点时，强烈建议将 etcd 从 Master 节点拆出来独立部署在 3 台专用高 IOPS NVMe SSD 服务器上，并在启动参数中调大空间配额 --quota-backend-bytes=8589934592（默认仅 2GB，写满会导致全集群只读锁死，调大到 8GB）。

3.2 深度解密：为什么发版或缩容时，前端总是偶发报 502 Bad Gateway？

这是 K8s 面试与生产排障的头号经典问题。
很多运维百思不得其解：“我已经配了 readinessProbe，应用代码里也开了优雅停机（Graceful Shutdown），为什么每次滚动更新杀老 Pod 的那几秒钟，Ingress-Nginx 还是会报几十个 502 Connection refused？”

根因：K8s 删除 Pod 时的“两条异步并发链路赛跑”！

当你删除一个老 Pod 时，APIServer 会同时通知两条完全独立、互不等待的链路：

  • 看懂悲剧是怎么发生的了吗？
    链路 A 跑得太快了！ 在第 0.01 秒时，容器已经把 8080 端口关门停业了；而此时链路 B 的 Ingress-Nginx 和 kube-proxy 还没收到“摘除这个 Pod IP”的通知！在接下来的 1 ~ 3 秒 时间窗口内，Ingress 还在源源不断地把新用户的请求转发给这个已经关门的旧 Pod IP，自然全部撞墙报 502 Connection refused！
  • 为什么 preStop: sleep 10 能完美根治？
    加了 preStop: sleep 10 后，链路 A 在发 SIGTERM 关停应用之前，会先原地等 10 秒（这 10 秒内老容器依然正常处理在途请求）；与此同时，链路 B 在第 2 秒就已经把全集群的 IPVS 规则和 Ingress 上游列表更新完毕，再也没有任何新流量发过来了。等到第 10 秒 sleep 结束，Kubelet 再发 SIGTERM 让应用体面退出——真正实现 100% 零 502 无损发布！

第四章：K8s 网络全链路打通：CNI、Service、CoreDNS 与 Ingress（中级篇）

4.1 CNI 容器网络插件怎么选？（Flannel vs Calico vs Cilium）

CNI 插件 常见网络模式 底层原理通俗解读 性能与特性对比 生产选型建议
Flannel VXLAN（Overlay 隧道） / Host-GW 把 Pod 发出的网络包封装在宿主机 UDP 包里（隧道封包解包），跨宿主机传输。 架构最简单稳定；但 VXLAN 封包会多占 50 字节头部（MTU 变为 1450），带来约 5%~10% 的性能损耗，且不支持 NetworkPolicy 网络隔离策略。 节点数 < 50 台、无需复杂网络安全隔离的中小集群首选，简单省心。
Calico IPIP（隧道） / BGP（纯三层路由直连） 利用 Linux 内核路由表和 BGP 协议直接广播各节点的 Pod 子网路由，无需隧道封包（BGP 模式）。 目前企业级生产占有率第一！BGP 模式下性能接近物理机原生网络，且原生支持强大的 NetworkPolicy 防火墙策略。 50 ~ 500+ 节点中大型自建机房（BGP）或云主机（IPIP/VXLAN）生产标准配置。
Cilium eBPF（内核字节码直通） 彻底绕过老旧笨重的 Linux iptables / netfilter 链，直接在内核 Socket 层通过 eBPF 完成转发与安全策略。 性能天花板！可彻底替代 kube-proxy，提供极强的 L7 可观测性（Hubble），但对宿主机 Linux 内核版本要求较高（建议 Kernel >= 5.10）。 高版本内核、超大规模集群（上千节点）或对网络性能/可观测性有极致要求的云原生团队。

4.2 终结 K8s 最诡异的“CoreDNS 5 秒解析延迟毛刺”！

很多团队上 K8s 后都会遇到一个极其灵异的现象：Pod 里的应用调外部接口（比如调微信支付 api.mch.weixin.qq.com 或内网 RDS mysql.internal.com），平时只要 2ms，但每隔一会儿就会莫名其妙卡顿整整 5 秒钟（5000ms）！

（1）两大真凶拆解

  1. 真凶一：/etc/resolv.conf 里默认的 options ndots:5 导致域名放大 5 倍查询！
    你可以进任意一个 Pod 执行 cat /etc/resolv.conf，会看到：
    • 什么是 ndots:5？ 它的意思是：如果你请求的域名里面，点号 . 的数量少于 5 个，Linux 解析器就会认为它不是一个完整域名，而是集群内部缩写！于是它会先把你的域名依次拼上 search 里的 3 个后缀去查一遍！
    • 举例：当你访问 api.mch.weixin.qq.com（里面只有 4 个点 < 5）时，Pod 竟然会按顺序向 CoreDNS 发起以下 4 次查询（每次还同时发 A 记录 IPv4 和 AAAA 记录 IPv6 共 8 个 UDP 包！）：
      1. api.mch.weixin.qq.com.prod-ecommerce.svc.cluster.local -> 返回 NXDOMAIN（不存在）
      2. api.mch.weixin.qq.com.svc.cluster.local -> 返回 NXDOMAIN
      3. api.mch.weixin.qq.com.cluster.local -> 返回 NXDOMAIN
      4. 最后第 4 次才去查真正的 api.mch.weixin.qq.com -> 成功！
  2. 真凶二：Linux 内核 nf_conntrack 处理并发 UDP DNS 包时的竞争丢包
    由于 glibc 同时并发发出 IPv4（A）和 IPv6（AAAA）两个 UDP 请求包复用同一个 Socket 源端口，在经过宿主机内核 DNAT 转发给 CoreDNS 时，两个包在 conntrack 表插入时发生冲突，导致其中一个包被内核静默丢弃！而 glibc 默认的 DNS 重试超时时间正好是 5 秒！

（2）生产环境一键根治方案

  • 方法 A（应用级最快解法，修改 Deployment 的 dnsConfig）：
    将 ndots 从默认的 5 调小为 2，并加上 single-request-reopen（避免 A 和 AAAA 记录并发冲突）：
  • 方法 B（集群级一劳永逸解法）：在集群中部署官方的 NodeLocal DNSCache（以 DaemonSet 方式在每台节点跑一个本地 DNS 缓存，并将 Pod 到 CoreDNS 的 UDP 升级为 TCP 连接），彻底消灭 5 秒毛刺并把 CoreDNS 负载降低 80%！

第五章：持久化存储（PV / PVC / StorageClass）与配置挂载深坑（进阶篇）

5.1 用“买房与切房”秒懂 PV、PVC 与 StorageClass

很多新手分不清 PV、PVC 和 StorageClass 的关系：

  • PV（PersistentVolume，持久卷）：相当于运维提前准备好的一套真实物理毛坯房（背面挂着真实的 NFS 目录、Ceph RBD 块设备或阿里云 ESSD 云盘）。
  • PVC（PersistentVolumeClaim，持久卷申领）：相当于研发提交的一张“租房申请单”（上面只写：“我要租一套 50GB、支持单机读写 ReadWriteOnce 的房子”，研发根本不关心底层是 Ceph 还是 NFS）。
  • StorageClass（存储类，动态供给）：如果公司有 1000 个微服务，每次研发提一张 PVC 申请单，难道都要运维手动去建一个 PV 吗？太累了！于是有了 StorageClass（全自动售楼处 + CSI 插件）——研发只要提交 PVC 并指定 storageClassName: ceph-rbd，StorageClass 就会自动调存储接口切出一块 50GB 的盘、自动创建出对应的 PV 并与 PVC 绑定（Bound）！

5.2 ⚠️ 运维高频踩坑点：为什么修改了 ConfigMap，容器里的配置文件却不自动热更新？

这是运维在管理 Nginx 或微服务配置时必踩的大坑：

  • 现象：你把 nginx.conf 放进了 ConfigMap 里，然后在 Deployment 里通过 volumeMounts 挂载到了容器内的 /etc/nginx/nginx.conf。某天你用 kubectl edit cm 修改了配置，等了 10 分钟，进容器看 /etc/nginx/nginx.conf 居然还是旧内容！
  • 根因揭秘（subPath 的致命副作用）：
    • 如果你是整个目录挂载（不写 subPath）：Kubelet 底层用的是符号链接替换，修改 ConfigMap 后大约 1 分钟内，容器里的文件会自动同步更新。
    • 但因为你不想覆盖 /etc/nginx/ 目录下的其他默认文件，你用了 subPath: nginx.conf 单文件挂载！在 K8s 设计中，凡是使用 subPath 挂载的 ConfigMap 或 Secret，容器内的文件永远不会自动接收热更新！
  • 正确解法：
    1. 要么把需要挂载的配置文件放在单独的子目录（如 /etc/nginx/conf.d/）下，去掉 subPath 直接挂载目录；
    2. 要么使用开源控制器 Reloader（stakater/Reloader），或遵循 GitOps 规范：每次修改配置时同步更新 Deployment Pod Template 的 Annotation（如 config-hash），触发 Pod 滚动更新。

事故二：Pod 陷入 CrashLoopBackOff 或 OOMKilled 无限重启循环！

什么是 CrashLoopBackOff？ 它的意思是：容器启动了，但里面的主进程（PID 1）很快就报错退出了！Kubelet 试图帮它重启，但它一启动又死了，于是 Kubelet 按指数退避（等 10s -> 20s -> 40s -> 最长 5分钟）循环重试。

3 步精准定位容器死因：

根据 Exit Code（退出码） 一眼定乾坤：

  • Exit Code: 137（Reason: OOMKilled，最常见！）：
    • $137 = 128 + 9$（代表收到了系统强制必杀信号 SIGKILL / kill -9）。
    • 两大诱因：① 容器实际内存突破了 YAML 里的 resources.limits.memory，被 Linux 内核 Cgroup OOM Killer 当场击毙（可在宿主机 dmesg -T | grep -i "Killed process" 看到铁证）；② Liveness 存活探针连续失败，被 Kubelet 主动强杀重启（在 describe pod 底部的 Events 里会看到 Liveness probe failed... Container will be restarted）！
    • 根治：若是内存不够，调大 limits.memory 并为 Java 加上 -XX:MaxRAMPercentage=75.0；若是启动慢被探针误杀，加上 startupProbe。
  • Exit Code: 143：
    • $143 = 128 + 15$（收到了优雅终止信号 SIGTERM / kill -15），说明是人为缩容、滚动更新或健康检查触发的正常关闭。
  • Exit Code: 1 或 127：
    • 业务代码自身抛出未捕获异常崩溃（如连不上数据库、缺少配置文件），或 127 启动命令路径写错找不到二进制文件。如果容器一启动 0.1 秒就死，连进容器排查的机会都没有，直接在 YAML 里加一行 command: ["/bin/sh", "-c", "sleep 3600"] 让容器先挂住不死，再 kubectl exec -it 进去手动跑启动命令看报错！

事故三：删除 Pod 或 Namespace 时，永远卡在 Terminating 状态删不掉！

事故四：Pod 狀態完全正常（Running 1/1），直接 curl Pod IP 是通的，但通过 Service ClusterIP 或 NodePort 却死活连不通！

请按以下 4 步排障清单 逐一核对，100% 能抓出问题：

  1. 第 1 步（看 Endpoints 有没有挂上 Pod IP — 80% 栽在这里！）：
    • 如果看到 ENDPOINTS 那一列是 <none>（空的）！说明你的 Service YAML 里的 spec.selector 标签选择器，跟 Deployment Pod 上的 metadata.labels 标签没有完全对齐匹配上（比如拼错了一个字母）！或者 Pod 的 readinessProbe 还没通过！
  2. 第 2 步（核对 targetPort 与容器真实监听端口）：
    Service 的 port 是虚拟端口，而 targetPort 必须完全等于容器内部进程实际监听的端口！
  3. 第 3 步（检查研发是不是把服务监听在了 127.0.0.1 上！）：
    如果研发在 Python/Node.js/Go 代码里写死了 listen("127.0.0.1:8080")，那么你在容器里面自己 curl 127.0.0.1:8080 是通的，但从 Service 或外部走 Pod 网卡 IP 进来全部报 Connection refused！容器内服务必须监听 0.0.0.0！
  4. 第 4 步（检查节点 ipvsadm 转发规则与 br_netfilter）：
    登录宿主机执行 ipvsadm -Ln -t <ClusterIP>:<Port> 查看是否有真实后端 RS 列表。

事故六：宿主机 df -h 看磁盘才用了 40%，但容器启动或写日志狂报 No space left on device！

当看到 No space left on device 而磁盘空间明明很空时，只有以下 3 种真凶：

  1. 真凶 A：磁盘的 Inode（索引节点）被海量 1KB 小文件耗尽了（100%）！
    • 立即执行 df -i！如果看到某个分区的 IUse% 是 100%，说明某个容器在 /var/lib/containerd 或挂载目录生成了数百万个碎片小文件，删掉对应目录即可。
  2. 真凶 B：文件已被删除，但进程还死死抓着文件句柄未释放（Deleted Files）
    • 执行 lsof -nP | grep '(deleted)'，找出占用几个 GB 已删除大日志文件的进程并重启它。
  3. 真凶 C（K8s 特有）：Linux 内核的 inotify 队列耗尽了！
    • 在 Linux 中，当 fs.inotify.max_user_watches 被占满时，很多程序报错信息也会诡异地提示 No space left on device！按第二章 2.2 节执行 sysctl -w fs.inotify.max_user_watches=524288 立即恢复。

事故七：集群突然有一批 Pod 变成 Evicted（被驱逐）状态，满屏飘红！

  • 为什么会出现 Evicted？
    当某台 Worker 节点的内存即将耗尽（MemoryPressure）或根分区磁盘超过 85%（DiskPressure）时，那台机器上的 Kubelet 为了保住宿主机不死机，会按优先级（先杀不写 resources 的 BestEffort Pod -> 再杀实际用量超过 requests 最多的 Burstable Pod）把它们强制踢死，并在原地留下一个状态为 Evicted 的尸体记录（同时控制器会在其他健康机器上把新副本拉起来）。
