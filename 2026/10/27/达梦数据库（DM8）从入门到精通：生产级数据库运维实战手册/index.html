第一章：初识达梦 DM8 —— 运维视角下的核心架构与存储模型（入门篇）

很多刚接触国产数据库（信创）的运维同学，一听说要接手达梦 DM8 心里就发怵。其实你只需要记住一句话：达梦 DM8 在管理语法、表空间、权限体系上 90% 像 Oracle，而在底层表存储结构（聚簇索引表）和单进程多线程模型上又吸收了 MySQL InnoDB 的优点！

1.1 一张表看懂 DM8 与 Oracle / MySQL 的核心差异（快速建立认知）

对比维度 MySQL (InnoDB) Oracle 达梦数据库（DM8） 运维核心注意点
进程/线程模型 单进程多线程（mysqld） 多进程架构（Linux 下十几个 ora_* 进程） 单进程多线程（dmserver） Linux 下只看得到 1 个 dmserver 主进程，内部由工作线程、I/O 线程、日志刷盘线程协作，内存开销低、切换极快。
实例与数据库关系 1 个实例下可建多个 Database（Schema） 1 个实例对应 1 个数据库（多表空间、多用户 Schema） 1 个 dmserver 实例对应 1 个数据库目录，内含多个表空间与多个模式（Schema） 如果一台服务器要建两个完全隔离的库，通常初始化两个不同端口（如 5236、5237）的实例，或在同实例下建多个 Schema。
用户（User）与模式（Schema） Database 即 Schema，与 User 完全解耦 创建 User 时自动拥有同名 Schema（1 : 1 绑定） 创建 User 时自动创建同名默认 Schema，且 1 个 User 可拥有多个 Schema（1 : N） 研发从 MySQL 迁过来最容易晕的地方：在 DM8 中连上 APP_USER，默认查的就是 APP_USER.表名！
默认表存储结构 索引组织表（IOT，主键即聚簇索引） 堆表（Heap Table，数据无序存放，ROWID 物理寻址） 默认是索引组织表（IOT，按主键或隐式 ROWID 聚簇有序存放） 既有 Oracle 的丰富 SQL 语法，又有 MySQL 按主键范围扫描极快的优势。
Redo 与 Undo 机制 Redo 存事务日志，Undo 存回滚段 Redo 存块变更 + Undo 变化，崩溃恢复需重放 Undo Redo 日志只记录数据页物理变更，Undo（ROLL 表空间）单独管理且不产生 Redo 神级特性：DM8 宕机重启时无需重放 Undo，实例崩溃恢复速度比传统数据库快数倍！

1.2 物理存储与逻辑存储全景映射（磁盘上到底有哪些文件？）

当你初始化一个达梦数据库实例（比如放在 /dmdata/DAMENG 目录下）后，登录服务器 ls -lh /dmdata/DAMENG，你会看到以下核心物理文件——运维必须知道每个文件坏了意味着什么：

文件/目录名称 对应逻辑概念 作用大白话解读 运维生死红线
dm.ini 实例主配置文件 相当于 MySQL 的 my.cnf 或 Oracle 的 spfile。控制端口、内存池、线程数、兼容模式等上千个参数。 修改前必备份；部分参数支持动态在线修改（SP_SET_PARA_VALUE），静态参数需重启实例生效。
dm.ctl 控制文件（二进制） 数据库的“户口本”。记录了数据库名称、魔数（DB_MAGIC）、所有表空间和 .dbf 数据文件的路径及检查点信息。 一旦损坏且无备份，数据库将无法 Mount 启动！ 生产环境会在 ctl_bak 目录自动保留备份。
SYSTEM.dbf SYSTEM 系统表空间 存放数据字典（有哪些表、哪些列、哪些用户权限）和全局系统信息。 严禁把业务表建在 SYSTEM 表空间里！
ROLL.dbf ROLL 回滚表空间 相当于 Oracle 的 UNDOTBS / MySQL 的 undo_001。存放数据修改前的旧版本镜像，用于事务回滚（ROLLBACK）和 MVCC 一致性读（防脏读）。 如果有未提交的超大长事务，ROLL.dbf 会疯狂自动扩展撑爆磁盘！
MAIN.dbf MAIN 默认用户表空间 如果创建用户或建表时没有指定表空间，默认全塞进 MAIN.dbf 里。 生产环境强烈建议为每个核心业务系统单独创建独立的表空间（如 TBS_ORDER.dbf），不要全塞在 MAIN 里。
TEMP.dbf TEMP 临时表空间 当 SQL 执行大排序（ORDER BY）、大分组（GROUP BY）、哈希连接内存不够用时，临时借用磁盘存放中间结果。 实例每次重启时会自动清空重建；也可以在线调用系统过程直接收缩释放空间。
DAMENG01.log / 02.log 联机重做日志文件（Redo Log） 循环覆盖写入的事务日志。客户端提交事务（COMMIT）时，只要 Redo Buffer 刷入此文件即代表事务持久化成功。 默认两个文件只有 256MB，生产高并发写入会导致频繁切换日志触发检查点卡顿，必须扩容到 2GB ~ 4GB/个！
arch/ 目录 归档日志目录（Archive Log） 在联机重做日志 DAMENG01.log 被循环覆盖前，后台 ARCH 线程把它完整拷贝一份存进归档目录。 开启联机热备和数据守护（主备集群）的前提条件！必须配置 SPACE_LIMIT 防止归档写满磁盘导致数据库挂起。

2.1 ⚠️ 运维第一生死铁律：dminit 初始化时“一旦建库终身不可改”的 6 个参数！

请把这一节打印出来贴在工位上！
无数新手运维在装达梦时，一路回车用默认参数跑完了 ./dminit 建好库交给了研发。结果研发导数据时狂报“记录超长”、“表名找不到（大小写问题）”、“字段长度截断”。这时候再去问原厂工程师怎么改 dm.ini——得到的回答永远是：“这 6 个参数是写死在底层数据页头里的，一旦 dminit 初始化完成，任何手段都无法修改！只能备份导出数据、删库重新 dminit 重建！”

dminit 参数名 官方默认值（极其容易踩坑！） 生产环境强烈推荐值 为什么默认值会害死人？（原理解析与选型标准）
PAGE_SIZE（数据页大小） 8（即 8KB） 32（即 32KB） DM8 规定单行记录（除大字段 LOB 外）的最大长度不能超过页大小的一半。如果用默认 8KB 页，表里几个 VARCHAR(2000) 一拼就会直接报错 [-2665]: 记录超长！生产环境一律设为 32！
EXTENT_SIZE（簇大小） 16（每个簇含 16 个页） 32（每个簇含 32 个页） 每次表空间分配连续页的最小单位。配合 PAGE_SIZE=32，将 EXTENT_SIZE 设为 32（即每次分配 1MB 连续空间），大幅减少大表碎片。
CASE_SENSITIVE（大小写敏感） Y / 1（默认区分大小写） 迁自 Oracle 选 Y (1)；
迁自 MySQL 强烈建议选 N (0)		 如果设为敏感（1），研發写 select * from user_info 和 USER_INFO 在加双引号时会被当成两张不同的表，且字符串比较 'abc' = 'ABC' 为假。若原系统是 MySQL，务必设为 0（不敏感）！
CHARSET / UNICODE_FLAG（字符集） 0（GB18030） 1（UTF-8） 默认 0 是中文国标 GB18030！现代 Java/Go 微服务与前端几乎清一色是 UTF-8，如果不指定 CHARSET=1，生僻字或多语言字符直接乱码！
LENGTH_IN_CHAR（VARCHAR 按字符还是字节算） 0（按字节 Byte 算） 强烈建议设为 1（或在 UTF-8 下配合业务评估） 在 UTF-8 下，1 个汉字占 3 个字节。如果原库定义了 VARCHAR(10) 存 10 个汉字，迁到 DM8 默认 LENGTH_IN_CHAR=0 下只能存 3 个汉字，第 4 个字就报字符串截断！开启 1 后自动放大字节上限。
BLANK_PAD_MODE（空格填充模式） 0 迁自 Oracle 设为 1，其余设为 0 控制 'a' 和 'a '（末尾带空格）是否相等。默认 0 严格区分，Oracle 迁移场景需设为 1。

第五章：高可用架构实战：数据守护（Data Watch 主备集群）与读写分离（进阶篇）

在金融、政务、能源等生产环境中，达梦最主流的高可用架构是 DM8 实时主备数据守护集群（1 主库 Primary + 1 实时备库 Standby + 1 独立确认监视器 Confirm Monitor）。

5.1 十分钟搞懂数据守护（Data Watch）的四大核心组件

不要被达梦一大堆 .ini 配置文件吓到，主备集群其实就是靠下面这 4 个部件协同工作的：

  1. MAL 系统（dmmal.ini）：达梦内部专用的高速 TCP 通信管道，主备库之间传 Redo 日志全走这个内部端口。
  2. 实时归档（dmarch.ini 中配置 TYPE = REALTIME）：主库在把 Redo 日志写入本地磁盘之前，先通过 MAL 管道发给备库。如果备库断联无法接收，主库为了防丢数据会自动先变为 SUSPEND（挂起） 状态，通知守护进程把备库标记为 INVALID（失效）后，主库立即恢复单机 OPEN 继续对外服务！
  3. 守护进程（dmwatcher）：主备机器上各跑一个 dmwatcher 服务，负责监控本机的 dmserver 进程，并在主备同步完成后自动把刚启动处于 MOUNT 状态的数据库 OPEN 打开。
  4. 监视器（dmmonitor）：分为两种模式（由 MON_DW_CONFIRM 控制）：
    • 非确认监视器（MON_DW_CONFIRM = 0）：只看不动，仅用于运维人员敲命令查看集群状态或手动切换，主库挂了备库不会自动升主。
    • 确认监视器（MON_DW_CONFIRM = 1，生产标配）：必须独立部署在第 3 台机器上！一旦主库宕机，确认监视器经过投票仲裁后，会自动指挥备库在几秒钟内执行 Failover 自动接管升为新主库！

5.2 ⚠️ 运维生死铁律：数据守护集群的“正确启停顺序”！

这是主备集群运维最容易酿成生产事故的地方！
如果计划内停机维护时，你顺手直接把主库的 DmService 关了，而没关确认监视器和守护进程——确认监视器会以为“主库出故障暴毙了”，当场下令让备库强行接管变成新主库！等你维护完把老主库一启动，就会引发主备冲突甚至分裂！

在 disql 或达梦管理工具（Manager）里，在慢 SQL 前面加上 EXPLAIN 即可查看执行计划：

执行计划操作符 英文全称 大白话含义与性能好坏判断 运维调优指向
CSCN2 Cluster Index Scan 全表扫描（聚簇索引全扫）！把整张表从第 1 页到最后一页全翻了一遍。 🔴 慢 SQL 头号元凶！大表出现 CSCN2 说明没建索引、索引失效（如隐式类型转换、对列用了函数）或没收集统计信息！
SSEK2 Secondary Index Seek 二级索引范围扫描！精准走到了你建的普通 B+ 树索引。 🟢 极佳！说明索引命中生效。
CSEK2 Cluster Index Seek 主键/聚簇索引精准定位扫描！直接通过主键 B+ 树定位到数据行，无需回表。 🟢 性能天花板！速度最快。
BLKUP2 Bookmark Lookup 回表查询！先通过二级索引 SSEK2 拿到主键 ROWID，再回头去主表里捞整行其余字段的数据。 🟡 若 BLKUP2 估算行数高达几十万行，随机 I/O 回表会比全表扫描还慢！可将查询列加进联合索引做成覆盖索引消除 BLKUP2。
HASH2 INNER JOIN Hash Join 哈希连接。把小表在内存中建成哈希表，扫描大表去匹配。 🟢 两张大表做等值关联（=）时的最佳连接方式（需确保 HJ_BUF_SIZE 内存充足）。
NEST LOOP INNER JOIN Nested Loop Join 嵌套循环连接。外层表每取 1 行，就去内层表查 1 次。 仅适合“小表驱动大表，且大表关联列有索引”的场景；若两张百万级大表走 NEST LOOP 会直接跑死 CPU！

[-2665]: 记录超长 表中存在多个 VARCHAR(4000) 字段，单行总长超过了数据页的一半，且未开启超长记录支持。 无需重建库！ 直接对该表启用“超长记录存储（将行外大字段转为 LOB 存储）”：
