第一章：初识 Nginx —— 运维视角下的进程模型、事件驱动与配置结构（入门篇）

1.1 为什么传统 Web 服务器扛几千并发就死，而 Nginx 能轻松扛 10 万并发？

很多运维新手会问：“Nginx 和老牌的 Apache（Prefork/Worker 模式）同样跑在同一台 Linux 机器上，为什么并发一上来 Apache 内存就爆了，而 Nginx 连大气都不喘？”

用“一对一服务员” vs “象棋大师车轮战（epoll）”秒懂底层差距

  • 传统多线程/多进程阻塞模型（如早期 Apache）：
    就像一家高档餐厅，每进来 1 个客人（TCP 连接），餐厅就必须专门雇佣 1 个专属服务员（进程/线程）全程站在旁边伺候。如果客人点菜时在刷手机思考（网络慢 I/O 等待），这个服务员就只能干站着傻等（线程阻塞挂起）。当同时涌入 10,000 个客人时，餐厅要雇 10,000 个服务员——光发工资（线程栈内存开销，每个线程数 MB）和大家挤在走廊里撞来撞去（CPU 上下文切换 Context Switch），就把餐厅直接搞垮了！
  • Nginx 的异步非阻塞 + epoll 事件驱动模型：
    Nginx 只雇佣了 与 CPU 核数相等（比如 8 个）的金牌服务员（Worker 进程）。每个 Worker 就像一位同时跟 10,000 个人下棋的象棋大师：
    • 谁举手说“我走好了”（Linux 内核通过 epoll 事件通知机制主动告诉 Worker：“第 88 号连接的数据包已经到网卡收齐了！”），大师就走过去花 0.01 毫秒走一步棋，然后立刻转身去处理下一个举手的人；
    • 那些还在思考没发数据包的连接，只占用几十字节的内存结构体静静躺着，完全不消耗任何 CPU，也没有任何线程切换开销！

1.2 Master + Worker 多进程架构与“零停机热重载（Reload）”原理

当你在服务器上敲 ps -ef | grep nginx 时，永远会看到两类进程：

进程角色 运行用户 核心职责 运维视角为什么这么设计？
Master 进程（包工头） root（因为只有 root 才有权限绑定 80/443 等 < 1024 的特权端口） 绝不处理任何具体的客户端网络请求！ 只负责读取校验配置文件、绑定端口、启动/监控/平滑重启底下的 Worker 子进程。 权限最小化安全隔离；哪怕某个 Worker 进程因为第三方模块 Bug 崩溃（Segmentation Fault）死了，Master 会在一毫秒内立刻重新 fork 一个新 Worker 顶上，服务不中断！
Worker 进程（打工人） 普通低权限用户（如 nginx 或 www-data） 真正干活的主力。通过 epoll 处理客户端连接、反向代理转发、SSL 加解密、读取静态文件。各 Worker 进程之间完全独立，互不通信（共享内存除外）。 Worker 数量通常设置为 CPU 物理核心数（worker_processes auto），一人霸占一个 CPU 核，彻底消除多进程抢核切换损耗。

面试与实战必考：执行 nginx -s reload 时，为什么正在下载文件的用户完全不会断连？

很多中间件一改配置重启就会闪断业务，而 Nginx 的 reload 是真正的优雅无缝切换：

  1. 运维执行 nginx -t && nginx -s reload（本质是向 Master 进程发送 SIGHUP 信号）。
  2. Master 进程先检查新配置语法无误，然后用新配置 fork() 启动一批全新的 Worker 进程（新 Worker 立即开始接收新的客户端连接）。
  3. Master 向老的一批 Worker 进程发送“优雅退休”指令：老 Worker 立即停止接收任何新连接，但会把手头上正在处理的旧连接继续服务完，直到最后一个数据包发送完毕后，老 Worker 才自动退出销毁！

1.3 nginx.conf 配置文件的五层嵌套结构与继承规则

看懂配置文件的层级关系，是避免报错 directive is not allowed here 的基础：

⚠️ 运维防坑铁律：add_header 与 proxy_set_header 的“全有或全无”继承陷阱！
在 Nginx 中，绝大多数普通配置指令（如 proxy_read_timeout）遵循“子块没配就继承父块，子块配了就覆盖父块”。
唯独数组型指令 proxy_set_header 和 add_header 是个巨大的坑：如果你在 http 或 server 块里配了 4 行通用的 proxy_set_header（比如传递真实 IP 和 Host），然后你在某个 location /special/ 里只要写了哪怕 1 行新的 proxy_set_header，那么外层 server 块里配的那 4 行 proxy_set_header 在这个 location 里会全部失效被清空！
最佳实践：把通用的 proxy_set_header 单独写成一个 /etc/nginx/proxy_params 文件，需要加特殊头的地方通过 include /etc/nginx/proxy_params; 显式引入！

第二章：生产级容量规划、OS 内核调优与标准化部署（入门到实战）

2.1 最大并发连接数计算公式（静态服务器 vs 反向代理）

当老板问你：“这台 8 核的 Nginx 网关，我把 worker_connections 配成了 65535，是不是就能同时扛 $8 \times 65535 \approx 52\text{ 万}$ 并发请求？”

请把下面这两个公式拍在桌子上：

  1. 场景 A：作为纯静态资源服务器（客户端 -> Nginx 读本地磁盘文件）
    $$\text{最大并发连接数} = \text{worker_processes} \times \text{worker_connections}$$
    因为每个客户端请求只消耗 1 个 Socket 连接（和 1~2 个本地文件句柄）。
  2. 场景 B：作为反向代理/负载均衡网关（客户端 -> Nginx -> 后端 Tomcat/Go/K8s Pod）
    $$\text{最大并发连接数} = \frac{\text{worker_processes} \times \text{worker_connections}}{2}$$
    为什么要除以 2？ 因为 Nginx 作为中间商，每接待 1 个外部客户端连接，自己还得再掏出 1 个连接去连后端的 Upstream 服务器！一进一出，1 个并发请求直接消耗掉 Worker 进程里的 2 个 connection 名额！
  3. 文件描述符（worker_rlimit_nofile）匹配铁律：
    在 Linux 中，“一切皆文件”，每一个 TCP Socket 连接都要消耗 1 个文件句柄（File Descriptor）。因此，在 nginx.conf 的全局块中，必须配置：
    $$\text{worker_rlimit_nofile} \ge \text{worker_connections} \times 2$$
    （通常 worker_connections 设为 65535，worker_rlimit_nofile 设为 131072 或 65535）。

第三章：路由匹配（Location）、Rewrite 重写与常见语法深坑（中级篇）

线上 80% 的 Nginx 路由故障（如页面 404、接口转发后路径少了一截、静态资源跳到了后端 Java），都是因为没彻底搞懂本章的三个核心机制。

3.1 location 五大匹配符号优先级铁律

当一个请求进到 server 块时，Nginx 并不是按你写配置文件的从上到下顺序傻瓜式匹配的，而是严格遵循以下 5 级优先级铁律：

优先级排名 语法符号 匹配规则通俗解释 命中后的行为 典型应用场景
第 1 名（最高） location = /uri 全字精确匹配（连多一个字符都不行）。 立即停止搜索，直接采用该块！ 网站首页 location = / 或高频健康检查接口 location = /healthz，速度最快。
第 2 名 location ^~ /uri 前缀排他匹配（注意：^~ 不是正则！意思是“只要以这个前缀开头，就别再去查下面的正则了”）。 如果命中了它且它是最长匹配前缀，立即停止搜索（跳过所有正则检查）！ 静态资源目录 location ^~ /static/，防止被后面的正则规则误伤截胡。
第 3 名 location ~ 表达式
location ~* 表达式		 正则表达式匹配（~ 区分大小写，~* 不区分大小写）。 按配置文件从上到下的书写顺序逐个匹配！谁写在前面先匹配上，就立即用谁并停止！ 匹配特定后缀文件：location ~* \.(gif|jpg|png|js|css)$。
第 4 名 location /uri 普通前缀匹配（不带任何修饰符）。 先找出所有匹配的普通前缀里最长的那个记住，然后再去跑第 3 名的正则；如果正则没命中，才用这个最长的普通前缀。 常规业务模块路由：location /api/v1/。
第 5 名（兜底） location / 通用兜底前缀匹配（因为任何 URI 都以 / 开头，长度最短为 1）。 当上面所有规则都没命中时，全部落入这里。 网站默认兜底转发或前端 SPA 路由。

一句话速记口诀：先找 = 精确；再找最长前缀（如果最长前缀带 ^~ 就直接收工）；否则按顺序跑 ~ 正则；正则全没中，回退用刚才记住的最长普通前缀！

  • alias（把 location 匹配到的那截路径整个替掉，换成 alias 目录）：

3.3 运维第二高频踩坑点：proxy_pass 末尾到底加不加斜杠 /？

这是无数研发和运维反复重启测试的噩梦。其实规则极其简单——只看 proxy_pass 的目标地址里除 IP:Port 外，有没有包含 URI 路径（哪怕只是一个 /）：

假设用户请求的完整路径是：http://域名/api/orders/list

序号 location 配置 proxy_pass 配置 区别特征 最终转发给后端的真实路径 原理解析
情况 1 location /api/ proxy_pass http://10.0.0.1:8080; 端口后面什么都没有（无 /） http://10.0.0.1:8080/api/orders/list 不带 URI：原样透传！把客户端请求的完整路径 /api/orders/list 原封不动传给后端。
情况 2 location /api/ proxy_pass http://10.0.0.1:8080/; 端口后面多了一个斜杠 / http://10.0.0.1:8080/orders/list 带了 URI（/）：截断重写（相当于 alias）！把匹配到的 /api/ 剥离截掉，只把剩下的 orders/list 拼到 / 后面！
情况 3 location /api/ proxy_pass http://10.0.0.1:8080/v2; 端口后面带了 /v2（无末尾 /） http://10.0.0.1:8080/v2orders/list（错误拼接！） 把 /api/ 替换成 /v2，直接跟 orders/list 连在一起变成了 /v2orders/list！
情况 4 location /api/ proxy_pass http://10.0.0.1:8080/v2/; 端口后面带了 /v2/（有末尾 /） http://10.0.0.1:8080/v2/orders/list 把 /api/ 完美替换成 /v2/，再拼上 orders/list。

更安全的做法是用白名单：

$upstream_connect_time Nginx 与后端服务器完成 TCP 三次握手所消耗的时间。 正常内网应为 0.000 ~ 0.002（2毫秒内）。
若高达 1.000s（剛好 1 秒，即 Linux SYN 重传时间），说明后端服务器负载过高、后端 Tomcat 的 acceptCount 全连接队列满了丢包，或者内网交换机丢包！
$upstream_response_time 从 Nginx 把请求发给后端，到后端处理完把响应全吐给 Nginx 所消耗的总时间。 如果这个值是 3.500s，而 $request_time 是 3.502s——100% 是后端应用（Java/Go/DB）慢！ 跟 Nginx 没有任何关系，把这条日志直接甩给研发！
$request_time 从客户端把第一个字节发给 Nginx 开始，到 Nginx 把响应的最后一个字节发回给客户端为止的全程总时间。 什么情况下 $upstream_response_time 只有 0.010s，但 $request_time 却高达 5.000s？
说明后端瞬间就处理完了，但：① 客户端用户的手机弱网（4G 信号差），上传大图片或下载响应包花了 5 秒；② 响应体太大（几 MB）卡在公网传输上！

8.2 六大经典生产事故应急排障 SOP（含 502 / 504 / 499 终极解剖）

事故一：502 Bad Gateway 突然暴增，如何 30 秒定位根因？

什么是 502？ 通俗说就是：Nginx 转身去找后端服务器要数据时，后端要么拒绝开门、要么直接把门摔在 Nginx 脸上（连接被重置），或者吐回来一堆 Nginx 无法解析的乱码/超大响应头。

排障第一步：永远先看 /var/log/nginx/error.log！ 根据报错关键字对号入座：

error.log 中的报错关键字 真实根因 秒级解决方案
connect() failed (111: Connection refused) while connecting to upstream 后端应用进程根本没启动、挂掉了（如 Java OOM 被杀），或者后端端口号配错了。 登录 $upstream_addr 对应的后端机器，检查应用进程与端口监听（ss -tlpn）。
upstream prematurely closed connection while reading response header 后端应用在处理请求半途突然崩溃退出，或者后端自身的 Keepalive 超时时间比 Nginx 的 keepalive_timeout 短（后端刚关掉长连接，Nginx 正好把新请求发过去撞上 RST）！ 将 Nginx upstream 中的 keepalive_timeout（如 60s）设置得小于后端 Tomcat/Go 的空闲超时时间（如 75s）。
upstream sent too big header while reading response header from upstream 最容易被忽略的 502！ 后端代码往响应 Header（如 Set-Cookie）里塞了超过 4KB/8KB 的超大数据，撑爆了 Nginx 的 proxy_buffer_size！ 在 http 或 location 中调大响应头缓冲区：
proxy_buffer_size 32k;
proxy_buffers 8 64k;
proxy_busy_buffers_size 128k;
connect() to 10.x.x.x:8080 failed (13: Permission denied) 新装的 CentOS/RHEL 机器开启了 SELinux，默认禁止 Nginx 进程主动发起外部网络连接！ 执行 setsebool -P httpd_can_network_connect 1 或关闭 SELinux。

事故二：504 Gateway Time-out 频发

  • 504 与 502 的本质区别：502 是后端“直接拒绝或断连”；504 是后端好好地连上了，但慢吞吞地一直算不出结果（比如卡在慢 SQL 或死锁上），超过了 Nginx 设定的等待时间，Nginx 等不耐烦主动切断并返回 504！
  • 查看 error.log 区分两种超时：
    1. upstream timed out (110: Connection timed out) while connecting to upstream：TCP 握手阶段就超时了（网络不通、防火墙丢包，或后端机器负载 100% 导致全连接队列满）。
    2. upstream timed out (110: Connection timed out) while reading response header from upstream：后端接口执行太慢，超过了 proxy_read_timeout（默认 60s）。
  • 处置方案：如果是特定报表导出/大文件处理接口确实需要跑 2 分钟，单独为该接口新建一个精准 location /api/export，单独设置 proxy_read_timeout 180s;（切勿把全局所有接口都改成 180s！）。

事故三：访问日志里出现大量神秘的 499 状态码（HTTP 标准里根本没这个码！）

  • 什么是 499 Client Closed Request？
    这是 Nginx 自己发明的专用状态码，意思是：后端还没处理完返回结果呢，前面的客户端（浏览器、手机 App 或上游网关）已经等不及，主动把连接关掉走人了！
  • 三大常见诱因与排障公式：
    1. 前端/调用方超时设得太短：比如前端 Axios 设置了 timeout: 3000ms（3秒），而后端接口实际跑了 3.5 秒。到第 3 秒时前端主动掐断连接，Nginx 就会记一条 $request_time: 3.000 的 499 日志！
      • 铁律：全链路超时时间必须呈“漏斗递减”或“上游大于下游”：客户端 Timeout（如 15s） > Nginx proxy_read_timeout（如 10s） > 后端 DB 查询 Timeout（如 8s）。
    2. 用户手快连点两次按钮 / 页面跳转：前端未做按钮防抖（Debounce），用户点完提交立刻刷新页面，前一个未完成的请求就会变成 499。
    3. 后端连接池被打满导致整体响应变慢：结合 $upstream_response_time 推动研发优化慢接口。

事故四：error.log 狂报 Cannot assign requested address (99)，偶发 502

  • 现象：压测或大促高峰期，CPU 和内存都很闲，但 Nginx 连后端突然大量报 99 错误。
  • 根因：Nginx 与后端 Upstream 没有开启 HTTP Keepalive 长连接，每次请求都新建一个短连接。由于四元组（源IP、源端口、目的IP、目的端口）中前三个固定，单台后端 IP:Port 最多只能并发建立约 2.8 万 ~ 5.5 万个连接，断开后端口全卡在 TIME_WAIT 状态 60 秒无法释放，本地临时端口彻底耗尽！
  • 根治组合拳：
    1. 立即按 第四章 4.2 节 为 upstream 配齐长连接三件套（keepalive 128 + proxy_http_version 1.1 + proxy_set_header Connection ""），TIME_WAIT 数量会在 1 分钟内从 5 万骤降到几十个！
    2. 检查系统内核参数 net.ipv4.tcp_tw_reuse = 1 和 net.ipv4.ip_local_port_range = 10240 65535 是否已生效。

事故五：执行多次 nginx -s reload 后，服务器内存爆满，出现几十个 worker process is shutting down 僵尸进程退不掉！

  • 现象：ps -ef | grep nginx 看到有几十个状态为 nginx: worker process is shutting down 的老进程挂着好几个小时不退出，吃光了服务器内存。
  • 根因：正如第一章所讲，老 Worker 必须等手头上所有的连接都断开后才会退出。如果你的业务有 WebSocket 超长连接、gRPC 流式连接，或者超长 keepalive_timeout，老 Worker 就会被这几个不断开的长连接一直吊着无法销毁！
