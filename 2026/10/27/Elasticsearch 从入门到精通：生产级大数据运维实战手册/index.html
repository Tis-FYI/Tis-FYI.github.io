第一章：初识 Elasticsearch —— 运维视角下的核心概念与架构（入门篇）

很多运维同学刚接触 Elasticsearch（以下简称 ES）时，容易被一堆专有名词绕晕。其实，你只需要把它看作一个自动分库分表、自带主从高可用、并且专门针对“按词查找”做了极致优化的分布式文件存储系统。

1.1 用“新华字典”和“分布式数据库”秒懂核心概念

（1）倒排索引（Inverted Index）与正排列存（Doc Values）

  • 为什么 MySQL 查 LIKE '%报错%' 慢，而 ES 快？
    • MySQL（正排遍历）：就像一本书没有目录，你要找包含“连接超时”的句子，只能从第 1 页翻到第 1000 页，逐行扫描（全表扫描）。
    • ES 倒排索引（专门用于搜索过滤）：就像《新华字典》的检字表。ES 在数据写入时，先把一句话拆成词（分词 Term），建一张“词 -> 包含该词的文档 ID 列表”的映射表。你搜“连接超时”，ES 直接查目录拿到文档 ID，耗时仅几毫秒。
    • ES Doc Values（专门用于排序和聚合 agg）：光有倒排索引还不够。如果老板要按“响应耗时”排序或统计每个服务报错次数，倒排索引就反而不方便了。于是 ES 在写入时还会默认生成一份列式存储（Doc Values），把所有文档的同一个字段紧凑地存在磁盘上，配合操作系统的页缓存（Page Cache），实现极速聚合与排序。
    • 运维启示：ES 之所以吃磁盘、吃内存，是因为你写进去一份 JSON 数据，ES 在底层帮你存了至少三份核心结构：原始 JSON（_source） + 倒排索引（用于搜） + Doc Values（用于算）。

（2）逻辑概念 vs 物理落地（运维最核心的认知）

以前教程总喜欢拿 ES 和 MySQL 做对比，但对运维来说，理解**“逻辑名称”与“磁盘上的物理实体”**的对应关系更为关键：

核心概念 通俗解释（运维视角） 物理上到底是什么？ 运维核心关注点
Document（文档） 一条日志记录或一条商品数据（JSON 格式）。 存储在分片内部的一条记录。 单条文档不宜过大（建议控制在 KB 级，避免几十 MB 的大字段写入）。
Index（索引） 具有相同业务属性的数据集合（比如 nginx-access-2026.10.14）。 纯逻辑概念（虚拟文件夹），本身不直接对应单个物理文件，由多个 Shard 拼装而成。 按天/按大小滚动创建，千万不能把全年几十 TB 日志塞进同一个 Index。
Shard（分片） 把一个大 Index 水平切分成多个小块，分布到不同机器上并行读写。 真正的物理干活单元！ 每一个 Shard 本质上就是一个独立的 Apache Lucene 实例，在 Linux 磁盘上对应一个独立的文件夹。 分片数过多会导致集群崩溃（分片爆炸）；单个分片建议控制在 20GB ~ 50GB。
Primary Shard（主分片） 负责接收写请求的分片，创建索引时数量固定。 物理 Lucene 目录。 一旦创建索引，主分片数量不可直接修改（改数量必须重建索引 Reindex）。
Replica Shard（副本分片） 主分片的完整拷贝，负责高可用容灾和分担读请求。 物理 Lucene 目录（绝对不会和对应的主分片放在同一个节点上）。 副本数量可以随时动态在线修改（如紧急扩容读能力，或大批量写入时临时置为 0）。
Segment（段） 一个 Shard 内部还会继续拆分成多个小文件块，叫做 Segment。 Lucene 文件夹下的 .cfs / .doc / .tim 等底层文件，具有不可变性（Immutable）。 段越多，查询越慢、越耗内存；后台会自动执行 Segment Merge（段合并），极其消耗磁盘 I/O 和 CPU。

1.2 节点角色全景解析与生产拆分原则

在测试环境里，一台机器往往身兼数职（既是裁判又是运动员）。但在生产环境中，如果不做角色隔离，一次复杂的聚合查询把数据节点内存打爆，就会连带导致集群主节点（Master）失联，进而引发全集群雪崩。

节点角色（8.x 配置名） 7.x 对应配置 角色职责通俗解读 硬件配置偏好 生产环境部署建议
Master-eligible（主候选节点） node.master: true 集群大脑/裁判。只负责管理集群元数据（有哪些索引、Schema 是什么、哪个分片在哪台机器上），绝不处理具体的文档读写。 低配即可（如 4C/8G 或 8C/16G），磁盘要求低，但网络必须极度稳定。 中大型集群必须独立部署 3 台专用 Master 节点（奇数台，防脑裂）。
Data（数据节点 / 热温冷分层） node.data: true 苦力运动员。负责存分片数据、执行倒排索引构建、全文检索和聚合计算。在 7.10+/8.x 中细分为：data_hot（热）、data_warm（温）、data_cold（冷）、data_content（内容）。 高配（如 16C~32C / 64G / NVMe SSD 大盘）。 核心计算与存储主力，按数据生命周期划分热节点（SSD）与温冷节点（大容量 HDD）。
Coordinating Only（仅协调节点） master/data/ingest 全设为 false 智能网关/负载均衡器。接收客户端请求，把请求转发给对应的数据节点，等数据节点算完后再汇总结果返回给客户端。 中高配 CPU 与内存（32G），无需大磁盘。 当业务有大量复杂聚合查询时，建议部署 2~3 台独立协调节点，防止汇聚结果时拖垮数据节点。
Ingest（预处理节点） node.ingest: true 数据清洗工。在数据真正落盘前，执行 Pipeline 管道（比如用正则切分日志、解析 IP 地理位置、转换字段类型），替代部分 Logstash 功能。 CPU 密集型（正则解析耗 CPU），无需大磁盘。 如重度使用 Ingest Pipeline，可与协调节点合并部署为网关层。

1.3 数据写入与查询的底层全链路（理解“近实时 NRT”）

面试和排障最常问的问题：“为什么数据写进 ES 后，要过 1 秒才能搜到？为什么不能立刻落盘？” 作为运维，看懂下面这四个动作，你就彻底掌握了 ES 性能调优的命门：

  1. Refresh（刷新，默认 1 秒一次）：把内存 Buffer 里的文档变成一个新的小 Segment 放进操作系统缓存（OS Page Cache），让数据可被搜索。
    • 运维调优锚点：每次 Refresh 都会产生一个新 Segment。如果大批量导数据时还保持 1 秒一次，会产生海量碎片小文件。把 refresh_interval 调大到 30s 甚至 60s，写入吞吐量能直接翻倍！
  2. Translog（事务日志，类似 MySQL 的 Redo Log）：因为 Refresh 只是把数据放进了操作系统的内存缓存（Page Cache），万一服务器断电，内存就丢了。所以每次写内存的同时，都会顺序写一份 Translog。默认是每个写请求都 fsync 落盘（最安全，但耗 I/O），如果允许极端宕机丢失 5 秒数据，可改为异步刷盘（index.translog.durability: async）。
  3. Flush（落盘，自动触发）：把操作系统缓存里的 Segment 真正调用 fsync 写死到物理硬盘上，同时删掉老的 Translog。运维通常不需要手动干预 Flush，但在重启节点前手动执行一次 POST _flush/synced（或直接刷盘），可以让节点重启后的恢复速度提升数倍。
  4. Merge（段合并，后台自动运行）：既然每秒 Refresh 都会产生一个小 Segment，一天下来岂不是有 86400 个小文件？文件句柄早爆了！所以 ES 后台有专门的合并线程，不断把十几个小 Segment 合并成一个大 Segment，并在合并过程中真正物理删除那些被标记为已删除（Deleted Docs）的数据。
    • 运维调优锚点：当你发现集群半夜没有业务请求，但磁盘 I/O 和 CPU 突然飙高，90% 是在做大规模 Segment Merge。对于不再写入的历史日志索引（如昨天的日志），运维可以在凌晨低峰期手动调用 _forcemerge?max_num_segments=1，释放磁盘空间并大幅提升查询速度。

第二章：生产级集群规划与标准化部署（入门到实战）

在生产环境中，“默认配置跑起来”等于埋雷。95% 的线上初期故障，都是因为部署时漏掉了操作系统参数或分片容量算错了。

2.1 硬件选型与容量评估公式

（1）黄金容量评估公式（接手新业务必算）

假设业务方找到你：“我们要把网关日志接入 ES，每天原始日志大约 500GB，要求保留 14 天，请帮我评估需要多少台服务器？”

请严格按以下四步计算：

  1. 计算膨胀系数（Inflation Factor）：JSON 明文变成 ES 索引后，加上倒排索引、Doc Values 和段文件开销，通常膨胀系数为 1.1 ~ 1.3（如果开启了复杂分词或多字段 multi-fields，按 1.5 算；若开启 best_compression 压缩，通常在 0.8 ~ 1.0）。我们按常规 1.2 计算。
  2. 计算副本倍数（Replica Factor）：生产环境为了高可用，默认配置 1 个副本（即 1 主 1 副，共 2 份数据）。
  3. 预留安全水位与后台开销（Overhead）：
    • ES 磁盘使用率达到 85%（Low Watermark） 就不再往该节点分配新分片；达到 90% 开始迁出分片。
    • Segment Merge 时需要临时双倍空间，还要留出约 10% 的操作系统预留。
    • 因此，磁盘可用空间最多只能按 70%（即预留 30% 空闲） 来规划。
  4. 总磁盘空间计算公式：
    $$\text{总所需物理磁盘} = \frac{\text{每日原始数据量} \times \text{保留天数} \times \text{膨胀系数} \times (1 + \text{副本数})}{0.7}$$
    代入上面的例子：
    $$\text{总所需物理磁盘} = \frac{500\text{ GB} \times 14 \times 1.2 \times (1 + 1)}{0.7} = \frac{16800\text{ GB}}{0.7} = 24000\text{ GB} \approx 24\text{ TB}$$
  5. 节点数与内存推导：
    • 单台 Data 节点的标准黄金配置是 16核 / 64GB 内存 / 4TB~6TB SSD。
    • 内存与磁盘的黄金配比（Memory-to-Disk Ratio）：
      • 高频实时检索/热节点（Hot）：建议内存与磁盘比为 1 : 16 ~ 1 : 32（即 64GB 内存的机器，挂载 1TB ~ 2TB 数据）。
      • 日志分析/温冷节点（Warm/Cold）：建议内存与磁盘比为 1 : 48 ~ 1 : 96（即 64GB 内存的机器，挂载 3TB ~ 6TB 数据）。
    • 对于本例（日志场景 24TB 总盘），按单机 64GB 内存 + 4TB NVMe SSD 计算，部署 6 台数据节点 + 3 台轻量 Master 节点 即可稳妥支撑。

（2）JVM 堆内存黄金法则：为什么绝对不能超过 31GB（32GB）？

这是运维铁律，包含两个核心原因：

  1. 必须留一半内存给操作系统（OS Page Cache）：ES 的底层引擎 Lucene 严重依赖 Linux 操作系统的文件缓存（Page Cache）来缓存 Segment 文件和 Doc Values。如果机器有 64GB 内存，你把 60GB 都分给 ES 的 JVM 堆，Lucene 读文件每次都要硬啃物理磁盘，性能会慢几十倍！因此，JVM Heap 最多分配物理内存的 50%。
  2. 不能突破 32GB 的指针压缩界限（Compressed OOPs）：在 64 位 JVM 中，只要堆内存小于 32GB，JVM 会自动开启“压缩普通对象指针（Compressed OOPs）”，用 32 位（4字节）寻址；一旦你配成 32g 或 33g，指针压缩失效，退化为 64 位（8字节）寻址，不仅白白浪费了约 15%~20% 的内存存指针，GC 停顿时间还会暴增！实际上，在分配达到 32GB 之前一点点（约 31.5GB），压缩就会失效。
    • 结论：无论物理机是 64GB 还是 128GB 内存，单实例 JVM 堆内存最大固定设置为 -Xms30g -Xmx30g（或 31g）。如果物理机有 256GB 内存怎么办？在一台物理机上通过 Docker/K8s 或多目录部署 2~3 个 ES 节点实例。

第四章：索引生命周期管理（ILM）与分片治理（中级篇）

如果说部署是盖房子，那么**分片与索引生命周期管理（ILM）**就是决定这个集群能安稳跑三年、还是三个月就崩盘的核心内功。

4.1 分片设计黄金法则（防“分片爆炸”与“大分片症”）

在生产环境中，关于分片有两句至理名言：

  1. “一个分片不是免费的！” 每一个分片（无论里面只有 1 条数据还是 1 亿条数据），都是一个独立的 Lucene 实例，都会在内存中维护倒排索引词典（Term Dictionary / FST）、占用文件描述符，并且 Master 节点必须管理它的路由状态。
  2. 经验黄金法则：
    • 单分片大小：控制在 20GB ~ 50GB 之间最佳（日志类冷数据最大不宜超过 50GB，高频搜索业务建议 15GB~30GB）。
    • 单节点分片总数：每 1GB JVM Heap 内存，承载的分片数量不要超过 20 个。举例：一台配置了 30GB 堆内存的数据节点，其上挂载的分片总数建议控制在 600 个以内（ES 7.x+ 默认硬限制 cluster.max_shards_per_node 为 1000）。

常见反面教材：分片爆炸（Oversharding）

很多新手为 50 个微服务分别按天建索引，每个索引无脑配 5主1副（即每天新增 $50 \times 10 = 500$ 个分片），其实每个微服务一天只有几 MB 日志。半年后，集群里有 9 万个几十 KB 的空壳小分片，导致 Master 节点内存撑爆、集群卡死！

  • 治理手段：
    1. 小数据量索引合并（或按月建索引，配 1主1副）。
    2. 彻底放弃“按固定自然日切分”，改用 ILM 按大小+时间自动滚动（Rollover）（比如满 150GB 或满 7 天才切新索引）。

4.2 索引模板（Index Template）与防止 Mapping 字段失控

ES 默认开启了 Dynamic Mapping（动态映射）：只要研发往 JSON 里塞一个新字段，ES 就自动识别类型并加进 Mapping。如果研发不小心把用户 ID 或动态 URL 当成了 JSON 的 Key（比如 {"user_1001": "ok", "user_1002": "fail"}），索引字段数会在几分钟内飙升上万，导致集群 Master 崩溃！

生产环境必须使用 Composable Index Template（组件化索引模板） 进行强管控：

模板亮点解析：

  1. strings_as_keywords 动态模板：默认情况下，ES 会把任何未知字符串同时映射为 text（分词全文检索）和 .keyword（精确匹配），白白浪费近一倍磁盘！通过上面的动态模板，把所有未显式声明的字符串默认只存为 keyword（且超过 256 字符不建索引），只有真正需要全文检索的 message 字段才显式指定为 text，直接省下 30%~40% 的磁盘与内存！
  2. index.codec: best_compression：启用 LZ4 换 Deflate（ZSTD）高压缩率算法，日志场景可再节省约 15%~25% 的磁盘空间，仅消耗极少量的 CPU。

4.3 ILM（索引生命周期管理）冷热温全流程自动化配置

运维最怕半夜两点被磁盘告警吵醒起床删日志。通过 ILM 策略，我们可以让 ES 自动完成以下流转：

  • Hot（热阶段）：当前正在写入的索引，放在 NVMe SSD 热节点上；当索引大小达到 120GB（3 个主分片，每个约 40GB）或写入满 1 天时，自动滚动（Rollover）生成新索引。
  • Warm（温阶段）：滚动下来的旧索引进入只读状态，满 2 天后自动迁移到普通 SATA SSD / HDD 温节点，自动将 Segment 合并为 1 个（forcemerge），并将副本降为 1。
  • Delete（删除阶段）：满 14 天后，自动物理删除该索引释放磁盘。

第六章：数据备份与灾难恢复（Snapshot & Restore）（进阶篇）

“副本（Replica）绝对不等于备份（Backup）！”
如果研发写错脚本执行了 DELETE /prod-orders*，或者代码 Bug 污染了全表数据，主分片和副本分片会在同一毫秒内一起灰飞烟灭。唯一的后悔药就是 Snapshot（快照备份）。

6.1 快照底层原理：为什么 ES 备份这么快且省空间？

ES 的快照备份是基于 Lucene Segment（段）级别的，并且天然全部是增量备份！

  • 因为 Segment 文件一旦生成就是**不可变（Immutable）**的。
  • 第一次拍快照时，ES 把所有 Segment 文件拷贝到远端仓库（如 S3/MinIO/NFS）。
  • 第二次拍快照时，ES 对比一下仓库，只拷贝上次快照之后新生成的 Segment 文件，之前已经备份过的 Segment 直接复用引用！因此日常定时拍快照对集群性能影响极小。

第七章：性能调优与深度排障指南（精通篇）

当集群规模达到上百 TB、写入峰值每秒几十万条（几十万 EPS）时，默认参数就会遇到瓶颈。本章总结了生产验证过的性能压榨方案。

7.1 写入性能极致调优（高吞吐日志/大促写入场景）

调优维度 具体配置 / 操作方法 为什么能提升写入性能？ 生产取舍与风险提示
1. 调大 Refresh 间隔 index.refresh_interval: "30s"（全量导历史数据时甚至可临时设为 "-1" 关闭刷新，导完再改回） 大幅减少每秒生成微型 Segment 的次数，降低后续 Segment Merge 的 I/O 压力，写入吞吐量可提升 50% ~ 100%。 数据写入后最长需要等 30 秒才能被搜到（对日志监控场景完全可接受）。
2. 调整 Translog 刷盘策略 index.translog.durability: "async"
index.translog.sync_interval: "5s"
index.translog.flush_threshold_size: "1024mb"		 默认 request 模式下每次 Bulk 请求都必须等待物理磁盘 fsync 完成才返回成功；改为 async 后每隔 5 秒刷盘一次，磁盘 IOPS 压力骤降。 若服务器发生硬断电或内核 Panic，该节点上最近 5 秒内写入且未刷盘的数据可能丢失（核心金融账务禁用，海量日志强烈推荐）。
3. 批量写入（Bulk）黄金大小 控制单次 _bulk 请求的物理体积在 5MB ~ 15MB 之间（条数通常在 1000 ~ 5000 条）。 请求太小会导致网络往返开销大；请求太大（如单次 100MB）会瞬间撑爆协调节点和数据节点的堆内存，触发 GC 停顿甚至 OOM。 务必按**字节大小（MB）**而非单纯按条数做客户端限流。
4. 使用自动生成的 _id 写入时不指定文档 _id，让 ES 自动生成有序紧凑 UUID。 如果业务自己指定 _id（如订单号），ES 每次写入前都必须先去该分片的所有 Segment 查一遍“这个 ID 是否已存在（判断是新增还是更新）”，白白耗费大量磁盘随机读 I/O！ 需要幂等去重的业务必须指定 _id；纯追加日志场景一律让 ES 自动生成 _id。
5. 全量初始化导数据时临时置 0 副本 导数据前：number_of_replicas: 0；导完后改回 1。 省去写入期间主副分片双倍索引构建开销，导完后再开启副本只做纯文件块拷贝，总耗时缩短近一半。 导数据期间无副本高可用保护。

7.2 查询性能调优与“防慢查询打死集群”机制

很多时候集群被打挂，不是因为写入太猛，而是因为某位研发在 Kibana 或代码里甩出了一个“毒查询（Query of Death）”。

（1）让研发遵守的 4 条黄金查询军规

  1. 能用 filter 绝不用 must：在 bool 查询中，如果只是做精确筛选（如时间范围、状态码 status=200、租户 ID），不需要算相关性得分（_score），一定要放进 filter 子句！因为 filter 不仅跳过算分 CPU 开销，还会自动利用 Node Query Cache（节点查询缓存，缓存 Bitset 位图），第二次查直接内存命中！
  2. 严禁使用左模糊通配符（wildcard: "*error*"）或复杂正则：以前缀 * 开头的查询，会导致倒排索引目录彻底失效，迫使 ES 全表扫描词典中的每一个词，CPU 瞬间飙红！如需模糊匹配，请在写入时使用 ngram 分词器或 wildcard 专用字段类型（ES 7.9+ 引入）。
  3. 严禁深度分页（from: 100000, size: 10）：
    • 原理剖析：如果你的索引有 10 个分片，你要查第 100,000 到 100,010 条数据，协调节点必须让每一个分片都把前 100,010 条数据捞出来排序，然后汇总 $10 \times 100,010 = 1,000,100$ 条数据在协调节点内存中二次排序，最后只取 10 条扔掉 100 万条！
    • 防线与替代：ES 默认限制 index.max_result_window: 10000。千万不要轻易把这个参数改成 100 万！ 深度翻页或全量导出请强制要求业务改用 search_after（带 PIT / Point in Time）。
    • PIT 创建时，ES 会在每个分片上固定住当时那一组 Lucene segment（一个只读的 searcher 视图）。之后拿这个 PIT 做的所有查询，看到的都是这份固定的数据：
      • 翻页期间的新增、更新、删除都看不到。
      • refresh 和 segment merge 也不会改变这个视图，因为被 PIT 引用的 segment 会被保留，不会被合并删掉。
      • 所以同一个 PIT 下，排序结果稳定，不会出现某条数据因为被更新而在两页之间”跳页”，造成重复或遗漏。
  4. 避免在高基数（High Cardinality）字段上做无限制嵌套 Terms 聚合：比如在有 1 亿个不同 user_id 的字段上做 size: 100000 的 terms 聚合，会瞬间触发熔断器报错。

（2）开启慢查询日志（Slow Log）抓捕线上毒查询

7.3 读懂 ES 的两大护城河：熔断器（Circuit Breaker）与线程池（Thread Pool）

很多运维看到 CircuitBreakingException 或 EsRejectedExecutionException 会慌神，其实这是 ES 在断臂求生，保护节点不被 OOM 搞死！

（1）内存熔断器体系（报错：[parent] Data too large, data for [...] would be [xxx/xxxgb], which is larger than the limit）

ES 在执行请求前会预估该操作需要消耗多少 JVM 堆内存，一旦超限直接拒绝该请求并返回 429，而不是任由它把整个 JVM 搞崩：

熔断器名称 配置参数与默认占 Heap 比例 负责拦截什么操作？ 频繁触发时的排障思路
Parent（父熔断器） indices.breaker.total.limit（开启真实内存统计 use_real_memory: true 时默认 95% Heap） 统计当前 JVM 堆内存的实际总占用率，是一切子熔断器的总闸门。 说明 JVM 老年代（Old Gen）内存长期居高不下！需排查：① 分片数是否过多占满基础内存；② 是否有大聚合查询未释放；③ 执行 POST /_cache/clear?fielddata=true 临时清理缓存救急。
Fielddata 熔断器 indices.breaker.fielddata.limit（默认 40% Heap） 当研发试图对 text 分词字段做排序或聚合并且开启了 fielddata: true 时，ES 会把整列倒排索引全加载进堆内存！ 严禁对 text 字段开启 fielddata: true！ 排序和聚合必须改用 .keyword 子字段（走磁盘页缓存的 Doc Values）。
Request 熔断器 indices.breaker.request.limit（默认 60% Heap） 拦截单次聚合查询（Aggregations）在内存中构建桶（Buckets）所消耗的临时内存。 业务写了多层嵌套 terms 聚合且 size 设得极大，联系研发优化聚合深度或拆分为多次查询。
In-flight Requests 熔断器 network.breaker.inflight_requests.limit（默认 100% Heap） 拦截当前正在通过网络接收的所有 HTTP/Transport 请求体（如超大的 Bulk 请求）占用的内存。 客户端并发发送了过大的 _bulk 请求包，减小客户端单次 Bulk 的 MB 大小。

（2）线程池队列与拒绝（报错：EsRejectedExecutionException: rejected execution of ... on EsThreadPoolExecutor）

每个节点内部针对不同任务维护了独立的线程池，最核心的是两个：

  • write 线程池（负责文档写入/删除/更新）：线程数 = CPU 核心数，默认队列长度（queue_size）= 10000（7.x 后期及 8.x 已调至 10000，早期版本为 200）。
  • search 线程池（负责查询/聚合）：线程数 = int((CPU核心数 * 3) / 2) + 1，默认队列长度 = 1000。
  • 为什么会出现 Rejected（拒绝）？
    当所有干活线程都忙不过来，新来的请求会进 queue 排队；一旦连排队队列（如 1000 个位置）也塞满了，第 1001 个请求就会被立即拒绝报错（HTTP 429）！
  • 运维禁忌：不要一看到 Rejected 就盲目去把 queue_size 调成 50000！队列越长，占用的堆内存越大，且请求在队列里排了 30 秒早就超时了。正确的做法是：查清为什么线程干活变慢了（是磁盘 I/O 满了？还是分片路由集中在单台机器上导致热点倾斜？）。

事故四：单台节点写入负载极高（热点倾斜 Hot Spot），其他节点却很闲

  • 现象：集群有 10 台 Data 节点，但只有 es-data-01 和 es-data-02 的 CPU 和磁盘 I/O 跑满，write 线程池开始出现 rejected，另外 8 台机器负载还不到 10%。
  • 根因剖析：当前正在高频写入的当天热索引（比如 prod-log-today），只设置了 2 个主分片！哪怕你有 10 台机器，这 2 个主分片（加上 2 个副本）最多也只能落在这 10 台机器中的 4 台上干活，另外 6 台机器只有昨天只读的老分片，根本分担不了今天的写入压力！
  • 根治方案：
    1. 主分片数应与热数据节点数量成整数倍匹配（例如有 6 台 data_hot 节点，高频写入的大索引建议设置 number_of_shards: 6，1 主 1 副共 12 个分片刚好均匀铺满 6 台机器）。
    2. 配置单节点单索引最大分片数限制，强迫同一个热索引的分片均匀打散到所有节点上，绝对禁止扎堆在同一台节点：

事故六：Master 节点频繁重选、Pending Tasks 堆积上千，建索引超时

  • 现象：报错 ProcessClusterEventTimeoutException 或 MasterNotDiscoveredException，_cluster/pending_tasks 里有成百上千个 create-index 或 put-mapping 任务。
  • 根因剖析：
    1. 集群总分片数突破了数万个，导致 Cluster State（集群状态元数据表）体积高达几百 MB，Master 每次修改完分片状态同步给几百个节点都要好几秒。
    2. 每天凌晨 00:00:00 整点，几百个按天切分的索引集中在同一秒钟触发创建（或者动态 Mapping 疯狂更新），把单线程处理元数据变更的 Master 节点彻底堵死。
  • 解决方案：
    1. 削峰错峰：将按自然日 00:00 集中创建索引，改造为 ILM 按大小+时间自动 Rollover，或者在凌晨 23:50 通过脚本提前预创建好明天的索引。
    2. 治理分片膨胀：删除过期索引、使用 _shrink 合并历史小分片索引，将集群总分片数压降到安全水位。
    3. 确保专用 Master 节点纯净：严禁往 Master 节点发送任何查询或写入请求（客户端负载均衡列表里只配 Coordinating 节点或 Data 节点，绝对不能填 Master 节点的 IP！）。
