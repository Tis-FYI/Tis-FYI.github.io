生产环境运维 Shell 实战手册

前言：在生产环境中，Shell 不是用来炫技的，而是用来解决问题和解放双手的。作为运维工程师，我们的脚本必须具备健壮性（防呆防错）、可读性和幂等性（多次执行结果一致）。本手册剔除了生僻语法，浓缩了十多年一线运维最常用的命令、技巧与脚本模板。

一、 命令行高频提效技巧（救急与日常）

在终端敲命令时，熟练使用快捷键和历史命令，能让你在障排查时快人一步。

1.1 终端保命快捷键

  • Ctrl + r：反向搜索历史命令（输入关键字即可匹配，极其好用）。
  • Ctrl + a / Ctrl + e：光标瞬间跳到行首 / 行尾。
  • Ctrl + u / Ctrl + k：删除光标之前 / 之后的所有内容（输错长密码或长命令时极有用）。
  • Ctrl + w：删除光标前的一个单词（以空格分隔）。
  • Alt + .（或 Esc 后按 .）：直接调出上一条命令的最后一个参数（比如先 mkdir /data/backup/20261111，接着输入 cd 然后按 Alt + . 就能直接粘过来）。

1.2 快速操作语法

  • !!：执行上一条命令（最常用场景：忘记加 sudo 时，直接输入 sudo !!）。
  • !$：代表上一条命令的最后一个参数（等同于 Alt + .）。
  • ^old^new：替换上一条命令中的某个字符串并执行（如上一条是 cat /etc/ngix/nginx.conf，输入 ^ngix^nginx 即可修正执行）。

  • cd -：在当前目录和上一次所在的目录之间快速切换。

生产脚本最怕变量为空导致灾难，学会使用参数展开（Parameter Expansion）：

  • "${var}"：所有变量引用必须加双引号和大括号，防止变量内含空格导致参数解析裂开。
  • ${var:-default}：如果 var 为空或未定义，则返回 default（不改变原变量值）。
  • ${var:?error_msg}：如果 var 为空或未定义，直接打印 error_msg 并强制退出脚本（校验必填参数神器）。

三、 条件判断与流程控制（实战用法）

3.1 永远使用 [[ ]] 而不是 [ ]

在 Bash 中，[[ ]] 是内置关键字，比传统的 [ ]（test 命令）安全得多：它不怕变量为空（不用狂加双引号防报错），且直接支持 &&、|| 以及正则表达式匹配 =~。

3.2 高频文件与状态判断参数

  • -e：文件或目录存在（Exists）
  • -f：存在且是一个普通文件（File）
  • -d：存在且是一个目录（Directory）
  • -s：文件存在且大小不为 0（常用于判断日志或导出文件是否成功生成）
  • -x：文件存在且有可执行权限
  • -z "$str"：字符串长度为 0（为空）
  • -n "$str"：字符串长度不为 0（不为空）

3.3 数值比较 vs 字符串比较

  • 字符串比较（在 [[ ]] 中）：使用 ==、!=。

七、 老运维的“血泪”避坑指南

  1. 永远不要直接写 rm -rf $DIR/*：如果 $DIR 因为某种原因未定义，这行命令会变成 rm -rf /*。请养成习惯写成 rm -rf "${DIR:?}/"*，或者先 cd "$DIR" && rm -rf ./*（得益于 set -e，如果 cd 失败脚本会直接停下，不会误删）。
  2. Crontab 环境变量坑：你在终端手动执行好好的脚本，放到 Crontab 里就报错 command not found？因为 Crontab 默认的 PATH 只有 /usr/bin:/bin。务必在脚本开头显式声明完整的 export PATH=...。
  3. Windows 换行符坑 (^M)：如果在 Windows 下用编辑器写好脚本传到 Linux，执行会报 /bin/bash^M: bad interpreter。用 dos2unix script.sh 或 sed -i 's/\r$//' script.sh 即可修复。
  4. 管道开启子 Shell 的坑：在 Bash 中，cat file | while read line; do count=$((count+1)); done 循环结束后，你会发现外面的 $count 依然是 0！因为管道 | 右边的 while 是在一个子 Shell 中运行的，变量修改无法传回父进程。请一律使用 while read line; do ... done < file 的重定向写法。
  5. 学会使用 shellcheck：在你的开发机或跳板机上安装 shellcheck（yum/apt install shellcheck），脚本上线前跑一下 shellcheck my_script.sh，它能帮你提前揪出 95% 的语法隐患和未加引号的坑。

八、 find -exec 与 xargs的用法对比和规范写法

find -exec 和 xargs 均用于将 find 查找到的文件作为参数传递给后续命令，但在进程创建开销、特殊字符安全性、参数位置灵活性以及并行能力上存在显著差异。

8.1核心维度对比

对比维度 find -exec ... \; find -exec ... + xargs
进程开销 极高（每个匹配文件启动一次进程） 极低（自动拼接参数，批量执行） 极低（自动拼接参数，批量执行）
特殊字符安全 原生安全（直接传递参数数组） 原生安全（直接传递参数数组） 默认不安全（按空格/换行分割），需配 -0
{} 占位符限制 可出现在命令任意位置，可多次使用 必须位于命令末尾，且只能出现一次 默认追加在末尾；使用 -I {} 可放任意位置
并行处理 不支持 不支持 支持（通过 -P 参数指定并发数）
标准兼容性 POSIX 标准（全平台通用） POSIX 标准（全平台通用） 跨平台参数略有差异（如 GNU 与 BSD）

8.2核心用法拆解

1. find -exec 的两种模式

  • 逐个执行（\; 结尾）：每找到一个文件就执行一次命令。适合必须单独处理每个文件，或占位符 {} 需要放在命令中间的场景。

    Bash

  • 批量执行（+ 结尾）：将查找到的所有文件尽可能多地拼接到一条命令末尾执行（受系统 ARG_MAX 限制自动分批），性能与 xargs 持平。

    Bash

2. xargs 的管道模式

  • 默认模式（不安全）：从标准输入读取数据，默认以空白字符（空格、制表符、换行符）作为分隔符。若文件名包含空格（如 my file.txt），会被拆分为两个独立参数导致报错或误操作。

  • 安全模式（-print0 + -0）：强制以空字符（\0 / NULL）作为分隔符，彻底规避特殊字符问题。

    Bash

8.3生产环境规范写法

在编写 Shell 脚本或执行高危操作（如 rm、mv、chmod）时，应遵循以下 5 条规范：

1. 严禁裸用 xargs 处理文件路径

凡是使用 xargs 接收 find 输出，必须成对使用 -print0 与 -0（若需兼容不支持 -0 的极老旧系统，优先改用 find -exec ... +）。

Bash

2. 防止空输入触发无效执行（GNU/Linux）

在 Linux（GNU xargs）中，即使 find 没有匹配到任何文件，xargs 默认仍会无参数运行一次目标命令（例如单独运行 rm 会报错）。应加上 -r（--no-run-if-empty）参数（macOS/BSD 默认已忽略空输入，但加上 -r 仍可兼容）。

Bash

3. 简单批量操作优先使用 find -exec ... +

如果目标命令支持接收多个末尾参数（如 rm、chmod、chown、tar），且不需要多核并行，直接使用 -exec ... +。它无需管道、无需记 -print0、原生防特殊字符且符合 POSIX 标准。

Bash
