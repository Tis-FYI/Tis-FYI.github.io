达梦数据库（DM8）索引运维与调优实战手册

达梦数据库（DM8）索引运维与调优实战手册

作者视角：10年+ 生产环境 DBA 实战经验总结
适用对象：数据库运维工程师、DBA、参与 SQL 审核的后端研发人员
核心理念：在生产环境中，“建对索引”只是及格，“不锁表、不抖动、可回退”才是资深运维的标准。

第一部分：核心认知——DM8 索引与 Oracle/MySQL 的本质区别

很多刚接触 DM8 的运维工程师会直接套用 Oracle 或 MySQL 的经验，结果在看执行计划和做空间规划时频频踩坑。在动手操作前，必须先搞懂 DM8 索引的三个底层特性：

1.1 默认表就是“索引”（索引组织表 IOT）

  • Oracle：默认创建的是堆表（Heap Table），数据无序存放，主键和二级索引都独立于表数据之外。
  • MySQL (InnoDB)：默认是索引组织表，**强制使用主键（Primary Key）**作为聚集索引（Clustered Index）。
  • DM8（重点！）：默认也是索引组织表，每张表都有且仅有一个聚集索引（CLUSTER INDEX），整张表的数据就是挂在这个聚集索引的 B+ 树叶子节点上的。
    • 潜规则 1：建表时如果不指定聚集索引，DM8 默认拿隐藏的物理行号 ROWID 作为聚集索引键！
    • 潜规则 2：在 DM8 中直接写 PRIMARY KEY 创建主键，默认生成的是 NOT CLUSTER（非聚集唯一索引），而不是聚集索引（除非建表时显式指定 CLUSTER PRIMARY KEY 或修改了 PK_WITH_CLUSTER=1 参数）。

1.2 为什么执行计划里 CSCN2 是全表扫描？

在 DM8 的执行计划中，你永远看不到类似 Oracle 的 TABLE ACCESS FULL（全表扫描），取而代之的是 CSCN2（Cluster Index Scan，聚集索引扫描）。

  • 运维秒懂公式：因为整张表的数据都存在默认聚集索引里，所以扫描聚集索引 = 全表扫描（CSCN2）！只要在大表上看到 CSCN2，就意味着没走二级索引，正在发生全表扫描！

1.3 常见索引类型及适用场景

索引类型 关键字 底层原理与运维适用场景 生产注意事项
二级索引（B+树） INDEX 最常用的默认索引。存储“索引键值 + 聚集索引键（通常是 ROWID）”。适合高选择性列（如订单号、手机号、身份证）。 增删改会带来索引维护开销，单表建议不超过 5~6 个。
聚集索引 CLUSTER INDEX 决定表数据在磁盘上的物理排序顺序。一张表只能有一个。极度适合按时间范围、连续 ID 批量扫描的场景。 严禁在大表业务高峰期新建或修改聚集索引，因为这等于把整张表物理重建并重新排序！
唯一索引 UNIQUE INDEX 保证索引列的值全局唯一（允许存在多个 NULL 值）。创建主键或唯一约束时系统会自动生成。 尽量用唯一索引代替普通索引，优化器能直接算出更精准的代价（Cost=1）。
函数索引 INDEX ON (FUNC(col)) 针对开发喜欢在 WHERE 左边写函数（如 TO_CHAR(create_time)、UPPER(name)）的场景，提前计算好函数结果建树。 查询时的函数表达式必须与建索引时一字不差才能命中。
位图索引 BITMAP INDEX 用二进制位（0/1）记录状态，适合低基数（重复值极多，如性别、状态码）且多条件 AND/OR 组合查询的数仓/报表场景。 OLTP 高并发交易库严禁使用位图索引！ 因为位图索引锁的是一个位图段，并发 UPDATE/INSERT 会引发全表级死锁！
全文索引 CONTEXT INDEX 用于对大文本字段（VARCHAR/TEXT/CLOB）进行分词模糊检索，替代低效的 LIKE '%关键字%'。 需注意分词器选择及增量同步策略（SYNC TRANSACTION）。

2.2 生产环境创建索引的“三条铁律”

在千万级、亿级大表上直接执行一句简单的 CREATE INDEX idx_xxx ON tab(col); 是初级运维最常捅出的生产事故——直接锁死表，引发业务连接池雪崩。

生产标准建索引模板：

  • 铁律 1：必须加 ONLINE 关键字
    • 不加 ONLINE 会对表加排他锁，阻塞所有业务增删改（DML）；加上 ONLINE 后支持在线创建，建索引期间允许业务正常读写（仅在开始和结束瞬间请求极短暂的字典锁）。
  • 铁律 2：表数据与索引表空间分离（TABLESPACE）
    • 生产规范建议将大表索引单独存放在独立的索引表空间（如 TBS_APP_IDX），不仅方便单独统计与维护，在多块物理磁盘环境下还能分散 I/O 压力。
  • 铁律 3：善用 PARALLEL 提速，但用完必须 NOPARALLEL
    • 对于亿级大表，加上 PARALLEL 4 或 8 可开启多线程并行扫描建树，速度提升数倍。但建完后如果不执行 ALTER INDEX ... NOPARALLEL，该索引的并行度属性会保留，导致日后高并发小查询走该索引时全部派生并行线程，瞬间打满服务器 CPU！

算子名称 全称 运维通俗解读 性能评级与调优方向
CSCN2 Cluster Index Scan 全表扫描（从头到尾扫一遍默认聚集索引）。 🔴 危险（大表出现必查，说明没建索引或索引失效）。

BLKUP2 Bookmark Lookup 回表操作（二级索引里只有 USER_ID 和 ROWID，拿到 ROWID 后回主表查 TOTAL_AMOUNT 等其他字段）。 🟡 关注（如果 SSEK2 扫出几行数据再 BLKUP2 很快；但如果扫出 50 万行再做 50 万次回表随机 I/O，比全表扫描还慢！）。
SSCN Secondary Index Scan 二级索引全扫描（把整个二级索引从头到尾扫一遍，不回表）。 🟡 一般（比全表扫描 CSCN2 快，因为索引体积比整表小，但通常说明没用上索引的前导列）。

3.2 算子组合实战解读案例

假设有如下执行计划输出：

  • 怎么读（从下往上，从第 5 行往第 1 行读）：
    1. 第 5 行 #SSEK2：通过二级索引 IDX_ORDERS_USER，精准定位 USER_ID = 10086，预估扫出 15 行（括号中间那个数字 15 就是预估行数 Cardinality）。
    2. 第 4 行 #BLKUP2：拿着这 15 行的 ROWID 回主表 ORDERS 捞取数据行。
    3. 第 3 行 #SLCT2：对捞出来的 15 行数据，在内存里过滤 STATUS = 'PAID'，最终剩 1 行。
  • 运维诊断结论：如果 USER_ID = 10086 实际有 10 万条订单，但只有 2 条是 'PAID'，那么第 4 步就会发生 10 万次无效回表！优化方案：把索引改成 (USER_ID, STATUS) 联合索引，先在索引层过滤完，只回表 2 次！

第四部分：疑难杂症——明明建了索引，为什么死活不走？（十大失效元凶）

这是日常运维被问得最多的问题。当你确认索引存在且状态为 VALID，但执行计划依然是 CSCN2（全表扫描）时，按以下清单逐一排查：

4.1 统计信息过期或缺失（占比 50% 以上！）

  • 原因：DM8 使用基于代价的优化器（CBO）。如果一张表刚建好时是空表，后来业务导进了 1000 万条数据，但没有收集统计信息，优化器还以为这张表只有 0 行！它觉得扫空表比走索引快，于是选择 CSCN2。

  • 现象：表中 PHONE（手机号）字段定义的是 VARCHAR(20) 字符串类型，且建了索引。但开发写的 SQL 是：
  • 原因：DM8 为了兼容执行，会在底层把 SQL 自动改写成 WHERE TO_NUMBER(PHONE) = 13800138000。相当于对索引列套了函数，直接导致索引失效！
  • 解决：督促开发严格对齐数据类型，字符串必须加单引号 '13800138000'。

4.3 违背复合索引“最左前缀原则”

  • 现象：创建了联合索引 IDX_ABC (A, B, C)。
    • WHERE A = 1 AND B = 2 -> ✅ 走索引
    • WHERE B = 2 AND C = 3 -> ❌ 不走索引 SSEK2（没有带大哥 A，B+ 树无法定位起点！）
    • WHERE A = 1 AND C = 3 -> ⚠️ 半走索引（只有 A = 1 能用于索引精准定位 SSEK2，C = 3 只能作为过滤条件）。

4.4 对索引列进行了函数运算、算术运算或左模糊匹配

  • 反面教材 1：WHERE TRUNC(CREATE_TIME) = '2026-10-31'
    • 正确改写：WHERE CREATE_TIME >= '2026-10-31 00:00:00' AND CREATE_TIME < '2026-11-01 00:00:00'（或创建函数索引）。
  • 反面教材 2：WHERE AMOUNT + 100 > 500
    • 正确改写：WHERE AMOUNT > 400。
  • 反面教材 3：WHERE NAME LIKE '%张%' 或 LIKE '%张'
    • 原因：前导通配符 % 无法利用 B+ 树字典序定位（注：LIKE '张%' 右模糊是可以走索引 SSEK2 的）。

4.5 使用了不等于（!=、<>）、NOT IN 或 IS NULL

  • 原因：B+ 树擅长找“等于什么”或“在什么范围内”，不擅长找“不是什么”。此外，DM8 的单列 B+ 树索引默认不存储全为 NULL 的记录，所以 WHERE COL IS NULL 默认无法走单列索引！

4.6 走索引回表代价高于全表扫描（优化器觉得走索引更慢）

  • 原因：如果查询条件 WHERE STATUS = 1 命中了全表 1000 万行里的 800 万行，走二级索引需要做 800 万次单块随机 I/O 回表（BLKUP2），而全表扫描（CSCN2）走的是多块连续顺序 I/O，优化器算出来全表扫描更快，就会主动放弃索引。

第五部分：高级进阶——分区表索引运维的“大坑”

生产环境中，超过几千万行或几十 GB 的历史流水表通常会做成分区表（Partitioned Table）。分区表的索引分为两类，一旦选错，日常分区维护就会变成灾难：

5.1 局部索引（Local Index） vs 全局索引（Global Index）

  • 局部索引（默认，强烈推荐）：每个分区自己管自己的索引树（1 个表分区对应 1 个索引分区）。

    • 巨大优势：当你月底清理历史数据执行 ALTER TABLE SYS_LOG DROP PARTITION P_202501; 时，对应的局部索引分区直接跟着秒删，其他分区的索引完全不受影响！

  • 全局索引（GLOBAL）：所有分区的数据共用一棵巨大的 B+ 树。

    • 运维大坑：一旦对分区表执行了 DROP PARTITION、TRUNCATE PARTITION 或 SPLIT PARTITION，整张表上的所有 GLOBAL 全局索引会瞬间全部变成 UNUSABLE（失效状态）！紧接着业务所有查询报错或全部退化为全表扫描，瞬间引发生产故障！
    • 避坑指南：
      1. 除非业务强制要求跨分区的全局唯一约束（全局唯一索引），否则尽量全部使用 LOCAL 局部索引。
      2. 如果存在全局索引，在删除/截断分区时必须加上 UPDATE GLOBAL INDEXES 子句（或者操作后立即 REBUILD 重建失效索引）：
